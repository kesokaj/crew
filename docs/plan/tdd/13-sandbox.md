## 13. Sandbox: one microVM per run

### 13.1 What runs where

Everything is built on Docker (R118). The core services are ordinary Docker containers. Every sandbox is also a Docker container, but one that Docker starts with the Kata runtime, so it runs inside its own small virtual machine with its own kernel.

**Docker is the only target.** You said in 0.32: everything runs in Docker, and Crew is built for Docker only. So there is no package and no other way to run Crew, and no part of Crew's own program runs as a process on the machine.

| On the machine, outside a container | Why it is there |
| --- | --- |
| Docker, and the Kata runtime with Cloud Hypervisor | They are what starts the containers. Kata is the runtime Docker uses for a sandbox. |
| The firewall rules, with the timer that puts them back | They must hold before any container starts, and when Docker restarts (13.6). |
| `crew-ctl` in `/usr/local/sbin/`, its files in `/usr/local/lib/crew/`, and the timer that lets it restart the machine | The script installs Docker and starts the containers. Its files are the host setup, the Kata configuration, the firewall, the units, the Compose file, and `versions.lock` (16.11). The timer, `crew-restart.timer` with its service, has it ask the server every 15 minutes whether the machine may restart (16.10). R118 names it apart from the three small systemd files below (since 0.67). |
| `/etc/crew/` | The answers, the key file, the secrets, and `install.json` (16.11). |
| The data folder, `CREW_DATA_DIR`, and the socket `/run/crew/updater.sock` | Files that containers mount: the database's files, the release folders, the backups, and the updater's socket. |
| The system user `crew`, and three small files under systemd | The owner of the folders. A drop-in that keeps Docker alive when memory runs out, and the firewall's service with the timer that puts its rules back (13.2, 13.6). Before 0.67 this row counted the restart timer as the third; it is `crew-ctl`'s, in the row above. |
| A kernel setting, and the packages the host setup added | KSM is switched on (13.2). The packages are the ones Docker and Kata need. |
| The machine's own security updates, and its restart | Debian's and Ubuntu's own unattended upgrades, for the distribution's security origin alone, with its settings in two files of `/etc/apt/apt.conf.d/`; they never restart the machine themselves. `crew-ctl` restarts it when the server says that nothing is going (16.10). |

- That is the whole list, and `install.json` records each part of it (16.11). No part of Crew's own program runs as a process on the machine: the server, the database, the ingress, the updater, every sandbox, and every hosted project are containers.

### 13.2 The hypervisor

| Hypervisor | Use it? | Why |
| --- | --- | --- |
| Cloud Hypervisor | Yes | styrman-crew runs it today and pins it in its host setup. It shares directories with the sandbox, which the home and the workspace need. |
| Firecracker | Not now | It cannot share a directory with the sandbox, so its disk must come from a special storage driver that Docker Engine does not offer. It works with containerd directly, not with plain Docker. Kata's newest runtime also leaves it out of its tested list. |
| QEMU | Fallback | It is the only one Kata tests under Docker Engine. It uses more memory per sandbox. |

Two things to know about the versions. Since 0.68 Crew runs Kata 4.3.1, of 2026-10-21, read upstream on 2026-10-24 with its advisories (section 24, item 13). Kata 4 rewrote its runtime in Rust: the static release `kata-static` holds runtime-rs alone, and the Go runtime that 3.31 used is a separate archive, `kata-go-static`, deprecated since 4.0 and given fixes only. Kata's own tests under Docker Engine cover QEMU only, and its guide for Docker uses the Go runtime, so Cloud Hypervisor under Docker with runtime-rs is a setup Kata lists but does not test: Crew's install test is the gate (16.11, its phase `kata4`). M1 tried Kata 4.2 on a fresh virtual machine: runtime-rs refuses a configuration named by `KATA_CONF_FILE` unless it is one of its compiled-in paths, which is how 3.31's shim wrapper named it; given as the runtime's `ConfigPath` option in Docker's settings, as kata-deploy does it, Cloud Hypervisor starts a microVM and shares a folder. runtime-rs also sizes a microVM another way: once, as it starts, as what its container asks for plus `overhead_vcpus` and `overhead_memory`, which Kata ships as 0.2 and 32 MiB, so a small sandbox, which asks for a CPU and no memory, would boot with 32 MiB. Crew's drop-in sets them to 1 and 2048, and every size is what it was on 3.31's base of 1 virtual CPU and 2 GB (13.10).

The machine is bare metal with Docker, used only for Crew. Bare metal has KVM, so no nested virtualization is needed.

**Where Crew can be installed.** On a bare-metal machine, or on a virtual machine with nested virtualization, because Kata needs KVM. The Linux is Debian based: Debian 13 or a current Ubuntu LTS. Other systems are refused by the host setup.

**How the Docker part is set up.** Crew adapts `deploy/host-setup.sh`, including its Google Compute Engine guest compatibility check. It is idempotent and run once as root (16.11).

| Step | What it does |
| --- | --- |
| 1. Check | It stops when the CPU has no hardware virtualization. Crew adds one check: it stops when `/etc/os-release` is neither Debian nor Ubuntu. |
| 2. Docker | Docker CE at the pinned `DOCKER_VERSION`, configured from Docker's official apt repository after `deploy/host-setup.sh` verifies `DOCKER_KEY_FINGERPRINT`. No user account joins the `docker` group; the server runs as system user `crew` (16.11). |
| 3. Kata | Kata Containers at a fixed version, as its static release: downloaded, checked against its SHA-256, and unpacked beside the Kata that runs, to `/opt/kata-<version>` (since 0.68; 3.31 was `/opt/kata`). It does not come from the distribution's packages, so it is the same on both systems. Kata's configuration of Cloud Hypervisor is never edited: two drop-ins of Crew's in its `config.d`, which runtime-rs merges into it and the setup checks by content on every run, move its paths into the folder, as kata-deploy's `10-installation-prefix.toml` does, and set the overhead of 1 virtual CPU and 2 GB, memory a guest frees given back, and no annotation taken from a container (`50-crew.toml`). A Kata newer than `versions.lock` is left as it is; an older one is moved from. |
| 4. Docker's settings | `/etc/docker/daemon.json` is merged, not replaced. It gets time namespaces off because Kata 3.31 refused them, IPv6 and `ip6tables` off, so a sandbox gets no IPv6 address, an address pool large enough for a network per sandbox, a log driver with size limits, and live restore on, so sandboxes keep running when Docker restarts. Docker is restarted only when the file changed. |
| 4b. The runtime | Since 0.68: Docker's runtime `mvm` names the Kata's shim by its path, `/opt/kata-<version>/runtime-rs/bin/containerd-shim-kata-v2`, with its configuration as the `ConfigPath` option. It switches only after a proof: the new Kata is first the runtime `mvm-next`, Docker reads its runtimes again on a reload, with no restart, and one microVM of the small size must have Kata's own kernel, 2 virtual CPUs and about 2 GB, and run on the new folder's shim, which the setup reads from the shim process that names the microVM's container, since Docker's info lists a runtime by its name only. After the switch's reload a microVM of `mvm` must run on that shim too. A proof that fails takes `mvm-next` out again and stops the setup, and `mvm` still starts the Kata that ran. containerd keeps each sandbox's shim by the path it started with, so sandboxes on the old Kata go on, and only what starts after the switch gets the new one. The folder of an older Kata goes in a later run, once no process runs from it or maps a file of it: it is renamed aside, looked at again, and removed, or renamed back. Only a folder `install.json` lists as Crew's (`kata_dirs`, and 3.31's `/opt/kata` with its shim wrapper when Crew installed them) is ever removed, and never one that any runtime in Docker's settings still names; a proof microVM has a name of its own, and every failure takes it and `mvm-next` out again. |
| 5. Protection | A systemd drop-in puts the Docker daemon last in line when the machine runs out of memory. |
| 6. Tuning | KSM is switched on, as styrman-crew does. On the 64 GB reference host with Kata 3.31 and Cloud Hypervisor it shares nothing: it scanned no page, because the guest memory is not marked as mergeable (section 24, item 6). It is kept switched on and counted for nothing. |
| 7. Folders and firewall | The state folders, owned by the system user `crew`, and the firewall with its timer (13.6). |
| 8. Security updates | Since 0.67: `unattended-upgrades` for the distribution's security origin alone (Debian's security archive, Ubuntu's security pocket), `Automatic-Reboot` false, and Docker's packages never (Kata is no package), with apt's daily run on; on Ubuntu also `update-notifier-common`. It stops when the producer of `/var/run/reboot-required` is missing: the kernel hook of `unattended-upgrades` on Debian, of `update-notifier-common` on Ubuntu. Then `crew-restart.timer` and its service (16.10). Probed on Debian 13 and Ubuntu 26.04 in M17. |
| 9. Proof | It starts one microVM and reads its kernel version. A sandbox has Kata's own kernel, not the machine's. |

- Apart from `apt` and systemd, which Debian and Ubuntu share, nothing in the script depends on the distribution.
- styrman-crew has only run it on Debian 13. Ubuntu is checked in M1, on the test virtual machine (section 24, item 34).
- styrman-crew's last step downloads the harness with a GitHub token while it builds the runtime image. Crew does not need that: its harness is in its own repository, so the image is built from the checkout with no token.

### 13.3 Kinds of sandbox

Every sandbox is a microVM, started by the same orchestrator. The one exception is the install test's machine, in the last row. ### 13.4 The runtime image

Every sandbox except a hosted project starts from the runtime image (R68) — or, since 1.37, from an optional per-project derived image `crew-project-runtime:<project>@<sha256>` built in a `Sources` build sandbox from `.crew/Dockerfile` (`FROM crew-runtime:<release>`) when the operator triggers `POST /api/projects/{p}/sandbox/build-image`; a run of the gate's `crew-gate` while a gate's live steps run starts from the candidate release's, by its id, and so does an agent run of a release's eval suite, whose subtask names it (16.2 step 5, 9.6, since 0.52). Only a run's sandbox takes an image so named: a check, a judge, and the improver never do, and a run that names one in a project that names its own is refused. An eval's subtask keeps its image, so a run that continues it after its suite ended, or after its gate left its live part, is refused: the image is a run's only while a release suite of its project from that image is open and its gate is live. It starts from styrman-crew's image. It holds `agy`, the harness built for it, and `crew-run` (12.8), and it is tagged with the release version, never with a moving tag.

| --- | --- |

| Crew | `crew-run`, added by Crew |
| Containers | Docker, buildx, compose |

The base is Debian, for AMD64 only. The daily look of 12.8 finds new versions of what `versions.lock` pins; the copy of styrman-crew's `bump-pins` script it replaces was removed in 0.56. ### 13.5 Inside the sandbox

- **Full access (R67).** The agent runs as a normal user that can use `sudo` without a password and is in the `docker` group. It can install anything and run containers in its own Docker daemon. It is not root itself.
- **Its own Docker.** The Docker daemon in the sandbox stores its data on a disk image in the run's home. Nothing the agent builds or pulls reaches the machine's Docker.
- **Project-scoped persistence and snapshots (since 1.37; hardened in 1.42).** In an ephemeral microVM what the agent installs is gone with the microVM. In a project's warm microVM (`crew-proj-<project>`), `<CREW_DATA_DIR>/projects/<id>/home` persists across runs (with credential-stripped, secret-key-sealed snapshots under `<CREW_DATA_DIR>/projects/<id>/snapshots/`, taken through `os.OpenRoot(home)` with `O_NOFOLLOW` while `active_sessions == 0` and with the running microVM paused during the read), while `crew-run` resets `.bashrc`, `.profile`, `settings.json`, and `config.json` before and after `setup()` (`PrepareRun`) through `os.OpenRoot`. A project's setup command (R70) runs in every new workspace of a role that builds or runs code, and in every check sandbox (11.2).
- **A setup command that fails twice** in a fresh sandbox gets a `fix` ticket. The project is not paused. You confirmed this. How it is built (since 0.47): `crew-run` runs the setup in the workspace before the CLI starts, so a failure uses no subscription. Two failures in a row in the project are checked on `main` first (12.4), and so are two check runs in a row of one open ticket that ended at the setup, which the runs of other tickets between them do not hide, so a branch that breaks the setup in its own check sandbox is not tried again without end in a busy project (since 1.12; the security review of 1.12's change, finding 1, and the operator's popup answer "Fix: per-ticket trigger"); a judge's answer between them does not count, since it runs no setup, and a closed ticket's two start nothing (since 1.12, its second round of review), except that on the setup's own fix ticket after it is Done, two marked outside check runs after a merge on GitHub start a check of the setup on `main` again even though the ticket is Done and was the setup's fix ticket (since 1.26, CREW-35, register row 12). The fix ticket is Crew's own, made as Crew makes its other fix tickets (origin `agent`, created by Crew), is analysed like an agent's, and sends news. Until it is Done, the runs that need the setup wait for it, as waiting for setup on their cards; its own builder starts with the setup's output and is not stopped by a failing setup. A check sandbox runs the setup too, so it counts in the two in a row; its setup that fails is not an error of Crew's that is tried three times, but waits as a run does, while Crew still tries the setup on `main`. Such a check run is marked as one whose setup failed, by the check sandbox's own error and never by its commands' names, and it is counted by that mark (since 0.95, 13.9). The fix ticket enters a stage that is full, because the tickets that fill it wait for it, and its own checks on `main` run without the setup, which fails there. While Crew runs the setup on `main`, and while the fix ticket is open, the runs and checks that need the setup wait, and their cards say so. When Crew could not run the setup on `main` three times, an error of its own and not a verdict, it stops trying and says so once in the news: no new run or check waits for it, and a ticket's check that ends at the setup on its branch counts as Crew's error, so the ticket waits after three, as for any error (since 0.75; the count since 1.12). A run whose subtask already waits for the setup, after it ended at it twice, waits on: neither a fix ticket nor a passing check on `main` comes to let it go (register row 10 in section 28, since 1.12). When it is Done, the branch of each ticket that waited is brought up to date with `main` by a merge without a work tree, so its new sandbox runs the fixed setup; a branch that conflicts stays as it is. Where the setup passes on `main`, a check that failed at it on a branch has failed, which is a fix round.
- **Not privileged.** The container has four added capabilities and is not privileged: `SYS_ADMIN`, `NET_ADMIN`, and `NET_RAW` for its own Docker, and `SYS_PTRACE`, without which that Docker cannot start a container that runs as another user than root (found in M1). The microVM is what makes that safe.

### 13.6 The network switch

Each project has a network mode, and a ticket can override it (R121). styrman-crew has the first and the third mode today. The second is new.

| Mode | The sandbox reaches | How | Status |
| --- | --- | --- | --- |
| Internet | The internet. Not the machine, not the local network, not other sandboxes. | The sandbox's bridge is named `sdb-…`. A firewall owned by root matches that prefix and drops every private address range, the link-local range, which holds a cloud's metadata address, the carrier range 100.64.0.0/10, and every address of the machine itself, the public one included. | In styrman-crew (its "sandbox" mode), with the last three added |

The CLI is given the server as its HTTPS proxy, and the proxy lets through only the hosts on a short list. | Since 0.43 (M10) |
| LAN | Whatever the machine reaches, including the local network | The bridge is named `lan-…`, which no firewall rule matches | Set by the operator on purpose |

| A hosted project (since 0.72) | `app-…`: the internet from inside, and no private range; `apo-…` (`hosting.internet` off): nothing beyond its bridge. Never the machine. On its bridge only the server and the ingress open a connection; the project answers them and opens none. | Two bridge prefixes, kept out of the modes a project, a ticket, a check or another sandbox may ask for. Machine setup 6. | Built in M19 |

- "No internet" cannot mean no network at all, because the agent's model is on the internet. Model only is the closest safe setting.
- The spike measured the hosts `agy` contacts, and it honours `HTTPS_PROXY` for all its traffic (section 24, items 3 and 65). `agy`: `daily-cloudcode-pa.googleapis.com` (the model), `aicode.googleapis.com`, `www.googleapis.com`, `antigravity-unleash.goog` (feature flags), `play.googleapis.com` (logs), and `lh3.googleusercontent.com` (the account's picture). `network.model_only_hosts` started from that list, and item 4 (M10) tried which of them a run can do without: not the feature flags and not the logs, but the account's userinfo and picture, which `agy` checks before a turn, and the login's renewal at `oauth2.googleapis.com` (spike/answers.md, item 4). The list has those five since 0.43.
- If a CLI does not use an HTTPS proxy, the same list is enforced on the bridge itself, by the name in the TLS handshake. That needs nothing from the CLI.
- In Model only mode a sandbox resolves no names itself. styrman-crew gives every sandbox two public resolvers. Crew gives a Model only sandbox none, and the proxy resolves the names on the list. Compose gives `crew-server` and `crew-caddy` the same two public resolvers (`dns: [8.8.8.8, 1.1.1.1]`, since 1.36), as styrman-crew's ingress has, so when Docker restores them at boot before DHCP writes `/etc/resolv.conf` on the machine, Docker's embedded resolver (`127.0.0.11`) still has external nameservers while resolving container names on the bridges.
- **The rules hold from the first packet.** They match the bridge prefix, not one bridge, so a new sandbox is covered before it starts. The timer only puts them back if something removed them, and they are put back when Docker restarts. No sandbox starts while the start-up test of the rules fails. Since 0.43 the test runs from inside each Model only sandbox before it is used: a connection to an address on the internet, or to the machine on its bridge, that succeeds removes the sandbox.
- **The proxy** is the server's door on the sandbox's bridge, where the broker answers. It takes `CONNECT` to port 443 of a host on `network.model_only_hosts`, by name, from a sandbox it knows by its door and address; it resolves the name itself and connects only to an address on the internet, never to the machine, a local network, or a range set aside. Every host it refuses is logged with the sandbox, which is how the list is measured. `agy` names no relay host for its remote control, so Model only mode's allowlist refuses any relay host not on those five, while Internet mode is not proxied (12.2; since 1.26, CREW-22, register row 73).
- **Go's modules come through the server** (since 0.61). proxy.golang.org answers the zip of a large module with a redirect to Go's bucket on `storage.googleapis.com`, which takes uploads to any bucket and is off `sandbox.sources` (L5 met it at `crew-caddy`'s build). So the door is also Go's module proxy for a Sources sandbox, and only for one: the server sets the sandbox's `GOPROXY` to the door's path `/goproxy`, and the door answers `GET /goproxy/<path>` for a path of Go's module proxy protocol (a module's `@v/list`, `.info`, `.mod`, `.zip`, or `@latest`) while `proxy.golang.org` is on `sandbox.sources`. The server asks proxy.golang.org for that path itself, as the tunnels do, at a public address on port 443, with nothing of the sandbox's request but the path, and follows one redirect, a GET, into `https://storage.googleapis.com/proxy-golang-org-prod/` and nowhere else; it hands on the answer, a 404 or a 410 as Go's command reads them, at most 512 MiB and ten minutes, and counts each request among the sandbox's tunnels. A method other than GET is a 405; a request from no sandbox, from one not in Sources, with `proxy.golang.org` off the list, or past the sandbox's 64 tunnels is a 403, which Go's command takes as an error, not a fallback; a path that is not of Go's protocol is a 404; anything else from Go's proxy or its bucket is a 502. A refusal of a sandbox the server knows, and each 502, has a log line that names the sandbox and why (the 405, the 404 of a path not of Go's protocol, and a request from no sandbox have none, as for the tunnels), and so does each 404 or 410 of Go's proxy (since 0.62), and a sandbox not in Sources is logged as refused itself, not as a refused host, so the list's measure is not touched. The answer is bounded by the same ten minutes for what it writes, so a sandbox that stops reading gives back its tunnel. There is no fallback to `direct`, and the checksum database's paths are not answered, so Go's command asks `sum.golang.org` itself through its tunnel and checks every module against it and `go.sum`; the server checks no hash. `make check` hands `GOPROXY` to its Go containers, `release.sh` hands it to each build as a build argument, and each Dockerfile stage that runs Go's command declares `ARG GOPROXY`, which is empty, and so Go's default, where no proxy is given, as on the machine. A Model only sandbox gets no `GOPROXY`, and the door refuses it.
- **What Sources lets out** (since 0.52). The proxy lets a Sources sandbox reach a host on `sandbox.sources` by its name, and no more: it checks no hash and no method. The module proxy (since 0.61) reaches Go's bucket, which is not on the list, only by the server's own GET of a path Go's proxy redirected to, so the sandbox sends nothing there. proxy.golang.org itself fetches a module it does not hold from wherever the module's path names, so a module path carries up to a kilobyte of what the sandbox holds to any host, 64 at a time, as the tunnel to proxy.golang.org on the list did before; such a path ends as a 404 or a 410, which the server logs with the sandbox and the path (since 0.62), and a module handed on is logged only at debug. Several of the hosts also take uploads, a push to GitHub, an image push, a package's publish, with credentials a build would bring itself. `storage.googleapis.com`, which 0.56 listed for `agy`'s tarball and which takes uploads to any bucket, is off the list since 0.57: the server downloads the tarball and hands it to the build (12.8); a machine that saved its own list keeps what it saved. So the build's sandbox can send out what it holds, which is Crew's own tree and nothing else: no secret, by the rule of 16.12, and no login. Crew's source is the operator's private code, which a run of an agent in Internet mode can send out as well. An inspecting proxy that lets only reads through would close it, and is not built.
- **The install test's machine** gets a bridge of the `sdb-` prefix, like a sandbox in Internet mode. So it reaches the internet for its packages, and not the machine, the local network, the core services, or a sandbox.

So have a conversation about a project and the chat of a ticket; a normal conversation outside a project takes the `network_mode` chosen for it (`internet` by default, or `model_only`, bounded by the machine's network mode, since 1.33). - Sandboxes can never reach each other, in any mode. That is Docker's own rule per bridge, and the server does not forward between bridges: Compose starts `crew-server` and `crew-caddy`, which join the sandboxes' and the hosted projects' bridges, with `net.ipv4.ip_forward=0` in their network namespace, where Docker's default is the machine's, which forwards, and a server in its container whose namespace forwards, or that cannot read whether it does, starts no sandbox, unless the operator sets `CREW_ALLOW_IP_FORWARD=1` in the install file, `crew.env`, which Compose is given by `crew-ctl` and by the updater and passes to the server, and `doctor` warns while it is set (since 0.83; a key of the install file since 0.85; the check server of a gate and the tiers' servers are started the same way). Forwarding off stops the server from routing; it still takes a packet for any of its own addresses on whichever bridge it arrives, and a sandbox's guest, root in its microVM, can send the server's address on another network through its own bridge, from any address of that bridge. So the ingress's door refuses a request that comes from any address on a sandbox's or a hosted project's bridge as well as one that arrives at the server's address there (20.3, since 0.85), and the broker knows a sandbox only by both its door and its own address. Both are known before the server joins a bridge at a sandbox's start, its adoption, and a hosted project's start, where the /24 is the bridge's own, which the project's stored addresses must be of (since 0.86). Before those two checks, the door answers only the ingress's network and the loopback (since 0.86, the operator's popup answer of session 51). The server learns that network at its start, before it serves, as the subnet of its own address that a name on that network alone gives: `crew-server-door`, Compose's alias on `crew-ingress`, which `CREW_DOOR_NAME` gives the server, asked as a rooted name, with a final dot, so a name Docker does not hold is never asked of the local network's resolver under the machine's search domain; the server's own name is not one, since Docker answers it with the bridge it joined last. A check server runs in a microVM, which Docker's name server does not answer, on its scratch network alone, and joins no bridge: its name there is its hostname, which Docker writes into its `/etc/hosts` with that network's address, and which is asked unrooted, since a rooted name is not looked up in that file. An address the name gives that is not the server's, as another container's under the alias while one is replaced, is passed over. A server that cannot learn it in a minute does not serve. The loopback is where Docker's health check and `crew admin` ask. The ingress's network holds the machine's own address on it, its gateway, so a process on the machine reaches the door, as it reaches the server's container anyway; that a guest's packet cannot come from that network rests on Docker's isolation of its networks, `crew-ingress` being internal, and on the server forwarding nothing, which `CREW_ALLOW_IP_FORWARD` set gives up. A guest cannot send from either and have the answer come back to it, so the door is closed to a guest also while the sandboxes do not know its bridge: while a server that started again in its container, still on the bridges of sandboxes that run on, has not yet taken them up, while a sandbox is removed, and on a hosted bridge after such a restart; and to IPv6, which the ingress's network does not carry.

### 13.7 What a sandbox does not share

| Thing | In each sandbox | Why nothing leaks |
| --- | --- | --- |
| Kernel | Its own | A microVM, not a shared-kernel container |
| Files | Its own project home (`<CREW_DATA_DIR>/projects/<id>/home`) and per-session git worktree (`/home/agent/worktrees/<run-id>`) | Each project has a separate directory on the machine, mounted into that project's sandbox only, and each ACP session works in its own worktree |
| Docker | Its own daemon and images | Stored on a disk image in the project's or run's home |
| Processes | Its own microVM, and per-session `agy acp --stdio --process-per-session` worker | Separate virtual machine per project, separate worker process per ACP session |
| Network | Its own bridge | No route between bridges |
| Identity towards Crew | Its bridge and per-session token | The broker, the MCP server, and the git endpoint know the session by the network it calls from, and by the bearer token given to that session in `NewSessionParams.mcpServers` |

A run passes something on in only two ways: by pushing commits to its own git branch, and by writing through the Crew MCP (R66). What Crew saves of the run itself, its trajectory and its conversation, is written by Crew, not by the run.

### 13.8 What protects the machine, and what does not

| Boundary | Mechanism |
| --- | --- |
| The machine's kernel and files | The microVM. A break-out from a container inside the sandbox lands in the sandbox's own kernel. |
| The machine's Docker | Never mounted into a sandbox. The server and the updater hold the Docker socket, and nothing else does. styrman-crew's ingress holds it too. Crew's does not (19.4). |
| Other sandboxes and the local network | One bridge per sandbox, and the root firewall |
| The canonical repository | Not reachable. A sandbox clones from and pushes to the quarantine repo, and only to its own branch. |
| The SSH key and the `gh` login | They stay with the server. A sandbox gets a GitHub token that can only read and stops working after one hour (12.6). |
| The database | No route from any sandbox's network. An agent reaches its project's data only through the Crew MCP (15.3). |
| Resources | CPU, memory, and disk per sandbox, and a timeout per run |

**What a sandbox does hold.** The login of the one CLI it runs and a GitHub token that can only read; no gcloud since 0.79. All of it is readable by the agent. An agent that is tricked by something it reads on the internet can use them or send them out, and the project's code with them. This is different from version 0.9, where the model key stayed outside. What limits the damage:

- The GitHub token cannot push, and it stops working after an hour. No run gets gcloud (12.6, since 0.79).
- What the `agy` login reaches beyond the CLI is not known yet. It is your personal Google account, and the spike checks it (section 24, item 27).
- Model only mode leaves a tricked agent almost nowhere to send anything: only the hosts its CLI needs, all Google's (13.6). What it sends inside TLS to such a host is not seen, so a tricked agent could still send data to a Google API on a listed host, such as `www.googleapis.com`, which `agy` needs (since 0.43).
- The work of a tricked agent still has to pass the other stages, and its trajectory records what it did.

Kata is a strong boundary, not an absolute one. Kata's list of advisories has several flaws from 2026 that reached the host. styrman-crew pinned Kata 3.31.0, from May 2026. ### 13.10 Capacity and cost

- **Start-up.** styrman-crew measures about 3 seconds from start to ready. styrman-crew then installs the harness into the new home, which takes about 13 seconds more. In Crew the harness is already in the image, so that step is gone.
- **Size.** Every microVM has 1 virtual CPU and 2 GB, and Kata adds what the container asks for: on 3.31 that was its base, and since 0.68 it is the overhead that Crew's drop-in gives Kata 4's sizing, which is fixed as the microVM starts (13.2). Crew sets a size per role: small for the lead, reviewers, and verifiers, larger for builders and testers that run Docker inside.
- **Overhead.** About 130 MB and a quarter of a core per microVM beyond what the guest uses. Memory the guest frees is returned to the machine. styrman-crew also turns on the sharing of identical pages between microVMs (KSM), but the spike found that it shares nothing with Cloud Hypervisor, so the capacity check does not count on it, and the side channel that sharing pages opens between virtual machines is not open. An idle small sandbox takes about 190 MB of the machine's memory, and an idle large one with its Docker daemon about 800 MB (section 24, item 6).
- **Networks first.** Without an address pool in Docker's settings (13.2, step 4), Docker gives out 29 networks besides its own, and every sandbox takes one, so 29 sandboxes is then a hard limit whatever the memory. The spike confirmed it on the reference host (section 24, item 6).
- **How many.** styrman-crew's own target is 10 or more running microVMs on a machine with 16 threads and 62 GB. The capacity check (7.9) uses each project's `sandbox.{cpus, memory_gb}` for warm project microVMs (`crew-proj-<id>`, counted once per project: `running` = full CPU and memory, `paused` = `0` CPU and full memory, `stopped` = `0` CPU and `0` memory, since 1.38) and the sizes in 14.1 for ephemeral sandboxes, so the number follows from the machine. Memory is counted strictly. CPU allowances are ceilings and may add up to more than the cores.
- **Networks.** Each sandbox takes one Docker network. The address pool styrman-crew configures has room for 4,096.

- **On a 16-thread / 64 GB reference host.** 12 cores with 16 threads, and 62 GiB, as the spike read it (section 24, item 57). After the reserve of 2 cores and 8 GB, 14 threads and about 54 GB are given out. The reserve of 8 GB is for the core services: their ceilings, the database's 2 GB, the ingress's 1 GB and the server's 4 GB with its pushes and fetches (6.1: in the git endpoint, `git http-backend` and the gits and hooks it starts run at an OOM score of 500, while the git endpoint's own short git reads and the import fetch do not), and 1 GB for the rest, so memory is not overcommitted when the server reaches its ceiling (since 1.08, the operator's popup answer of session 75 "4g ceiling, reserve 8 GB"; it was 4 GB, of which 2 GB the database's, while the server had no ceiling). By memory, counted strictly, a small sandbox takes 2 GB and a large one 6 GB (the build of a release 8 GB, since 0.60), so 15 would fit: for example 6 builders or testers and 9 leads, reviewers, and verifiers, which is 54 GB. By CPU, with `cpu_overcommit: 2.0`, the ceilings may add up to 28 virtual CPUs, and those 15 would ask for 42, so about 10 fit: for example 4 large and 6 small. CPU is what bounds the count on that reference host. What a run really used in the spike is small: a large sandbox working with either CLI used 370 to 650 MB of memory (at most about 1 GB) and a few percent of its CPU, because an agent mostly waits for its model (item 26). The subscription bounds the work first: `agy` carries about one run without a break (item 35). So the sizes and the overcommit stay as they are (parked question 101). A conversation or a chat of a ticket is a large sandbox, and the capacity check counts it like a run: while one is open, one builder or tester fewer starts. Three can be open at once. Spike item 81 says whether a small one does for most questions. A hosted project takes its room first.
- **What that means.** One project at its default limits can ask for more than a 64 GB host has. With several projects running, runs wait for room, and the Projects screen shows what waits. The spike measures what a run really uses, so the sizes can be lowered (section 24, item 26).
- **Disk on the host machine.** The host disk holds the database, the repositories, the images, the homes of running sandboxes, the hosted data, and the backups. The disk guard cleans up before it is full (16.10).

### 13.11 Terminals

A terminal is first of all for diagnostics and troubleshooting (R140). The project terminal also has an edit mode, for the times the operator needs to go in and do the work by hand.

| A ticket where a subtask is running | Directly inside that run's microVM, where the agent is working: the same files and the same processes. When several subtasks run in parallel, the operator picks the run. |
| A ticket where nothing is running | The project terminal, switched to that ticket's branch. |

**The project terminal has two modes.**

| | Diagnostics (the default) | Edit mode |
| --- | --- | --- |
| For | Looking, running, and trying things | Changing the code yourself |
| The repository | The git endpoint takes no push from it. Commits stay in the terminal. | Can be pushed. |
| Pushing to `main` or to a branch of your own | Refused | Accepted. - **A sandbox like any other.** The project terminal has its own microVM and the project's network mode. It is started when asked for, and removed when it is closed or after 30 minutes without input. There is one per project.
- **What it holds.** What a run of the project holds. It also holds the logins of every CLI that is signed in. So a CLI can be started by hand: to see why it fails, or in edit mode to work with it.
- **While an agent is running on a ticket.** A push to that ticket's branch is refused, so the operator and an agent never change the same branch at once. To step in there, jump into the run's microVM, or put the ticket on hold first.
- **Inside a running run.** The operator is in the agent's own sandbox and can do what the agent can. That is the point when something is stuck.
- **Nothing is hidden.** Opening a terminal and switching to edit mode are entries in the ticket's or the project's history. What was typed and printed is saved in the database, for 180 days, sealed with the key of the credentials, at most 16 MB of one attachment. The operator's commits carry the operator's name.
- **Edit mode lasts while you are there.** When no page is on the project terminal any more, it is back in diagnostics mode, so nothing left running in it pushes in your name. A `main` pushed from it that changes a file that is code for the agent CLI, or a workflow, is held for your confirmation like any other, and the inbox names those files first, as no such change merges by itself (13.8; since 0.42). A `main` Crew does not take is in the project's history with the reason.
- **Not how agents are driven.** Agents stay headless.

### 13.12 ComputeRuntime: Docker + Kata today, suspend/resume, and Kubernetes seam (M21 to M26, since 1.47)

Crew already runs isolated Docker + Kata warm project microVMs (`crew-proj-<project>`, `internal/orchestrator/project_vm.go`) with live `PauseSandbox`/`UnpauseSandbox` cgroup freeze/thaw (`ContainerPause`/`ContainerUnpause`, `0%` CPU while preserving memory state) and credential-stripped, secret-key-sealed `.tar.gz` home snapshots (`SnapshotProjectHome`/`Restore`, `512 MB` cap, `internal/sandboxes/snapshot.go`) alongside throwaway check sandboxes (`13.9`).

- **`ComputeRuntime` interface (`internal/sandboxes/runtime.go`, `R219`):** Formalizes those existing Docker + Kata capabilities behind one explicit backend interface: `Start`, `Exec`, `Suspend`, `Resume`, `Snapshot`, `Restore`, `Stats`, and `Destroy`.
- **Docker + Kata as Tier-1:** Keeps the runtime host strictly Docker-only (`AGENTS.md`), mapping `Suspend`/`Resume` directly to fast cgroup pause/unpause for warm idle VMs and `Snapshot`/`Restore` to sealed `.tar.gz` archives stored in `BlobStore` (`Local FS` or optional `GCS`, `5.1`, `R220`).
- **Kubernetes seam (`RuntimeClass: kata`):** Defines the future cluster-driver mapping against the same `ComputeRuntime` contract, where `Suspend` snapshots `/home/agent` into `BlobStore` (`GCS` or object store) before pod eviction and `Resume` restores the snapshot into a fresh Kata pod without changing `Tasks API` or `Agent API` callers.
