## 16. Versions, self-update, and roll back

Crew collects signals from every project, so Crew is also where its own improvements are made. Crew must be able to update itself from inside the app, every version must be clearly numbered, and any version must be one click away (R110 to R117).

The updater is new. styrman-crew's updater worked only so-so, so it is not copied. Its bug records show why, and each point has an answer here.

| In styrman-crew's updater | What went wrong | In Crew |
| --- | --- | --- |
| It fetches new tags from GitHub with a token kept on the machine | The token was rejected, and one machine stayed on an old version for ten days without anyone noticing | A release is built on Crew's own machine. Updating fetches nothing. |
| It builds the new version from source on the machine while updating | It is slow, and what runs is not what was tested | The images are built once, tested, and kept. The update uses those exact images, checked by their content hash. |
| It installs only tags signed by a trusted key | A tag signed by the wrong key was pushed and refused, and a key was exposed once | A release is what passed the gate, named by its content hash. You get a notice, and you decide when code is installed. There are no signing keys to keep (16.3). |
| It replaces the running version and checks health afterwards | A bad version means downtime until the roll back has rebuilt the old one | The new version is started and checked beside the running one. Nothing is replaced until it has passed (16.4). |
| Rolling back rebuilds the old commit | Slow, and a build can fail | The old images are kept. Rolling back switches to them (16.5). |
| A root shell script of about a thousand lines on a timer, which also updates itself | Bugs with root, with files of other users, and with new files that the old script never installed | A small program in its own container, with tests. It never replaces itself (16.8). |
| It also changes the machine's setup on every tick | A failed version stopped those changes | The machine's setup is separate and has its own number (16.4). |

### 16.1 One version for everything

A Crew release has one number, `X.Y.Z`, and that number fixes every part that affects how Crew or its agents behave.

| Part | Fixed as |
| --- | --- |
| The server and the UI | Image `crew-server:X.Y.Z` |
| The ingress | Image `crew-caddy:X.Y.Z` |
| The runtime image | `crew-runtime:X.Y.Z`: the tools, `agy`, the harness, and `crew-run` |
| The updater | Image `crew-updater:X.Y.Z`. The server installs it after it has been healthy on the new version (16.8). |
| Crew's stage prompts and pipeline defaults | Files in the server image |
| The database | The version of PostgreSQL in `crew-db`, and the schema number the release needs |
| The machine setup it needs | A number. Most releases need the one already installed. |

- A release is a folder on the machine: the images as files, and `release.json`, which lists every part with its content hash. The app shows it for every version. Since 0.48 it also lists the files of the commit with their git hashes, and the model line of each agent file, so the running version can tell which kind a release is without a checkout (16.3).
- There are no moving tags such as `latest`.
- Every run record names the Crew version it ran on. So results can be compared per version, and a change in results can be traced to a release.
- A baseline change (section 10) is delivered as a release like any other change. The improvement, the eval results, and the measured effect are attached to that release.
- When `updates.publish` is enabled, every release's tag, release notes, and built images (kept private by default for runtime images containing vendor CLIs, 16.9) are pushed to the configured repository and registry. That copy is outside Crew and can be pulled by secondary installations (16.12).

### 16.2 Crew builds Crew

Crew's own code is a project on its own board.

- **Crew's project** (since 0.51). The Crew level has one button, Make Crew's project. It imports the repository that `updates.source_repo` names (e.g. `your-org/crew`) as an ordinary project, and sets `improvements.crew_project` to it. There is one: the button refuses a second, though a press that made the project but not the setting is finished by the next (since 0.52). The project's remote must be `updates.source_repo`, which is checked when a save changes either, and `updates.source_repo` must be `owner/name`; the project is always `Protected` (7.13, since 1.34: locked on, and neither archived nor deleted, while `makeGate` and schema step 83 archive the M4 `fixture` project so it leaves the lists). Until M20 the operator's own coding agent keeps building on `main` from its checkout; Crew's project takes those pushes as work from outside (row 11: taken and checked), as any project does, and its merges wait while a `remote_mains` row is `checking` or while the open fix ticket of a failed `ahead` row exists, while unrelated tickets' `PurposeMerge` checks and their fix rounds still run (7.12; since 1.26, CREW-34). Crew's agents work only the tickets that are put on its board. **It is never Done** (since 0.55, the operator's answer 2 of report 10): it has no plan, and its board takes tickets for as long as Crew runs, so it is running or paused, and the operator can pause it. Its last ticket's Done runs only that ticket's own steps: no retrospective at Done, no final report, and no tag `done`. On an early build host its first ticket made it Done, which ran all three, pushed the tag `done` to GitHub (a tag is never moved), and left it unable to pause; schema step 65 pauses it again. **Its checks** (since 0.53, the operator's choice of report 8): `make check`, with no setup, in a check sandbox, which has a Docker daemon of its own and no socket of the machine, in the network mode Sources (`sandbox.check_network`, 13.6), as the build's `make check` runs; its runs get no gcloud (`credentials: []` until 0.79, when no run gets it), and keep the project's own mode, since Sources lets the package sources through and not the model's hosts. Make Crew's project gives these settings, and schema step 61 gave them to the project made before: the one the machine's `improvements.crew_project` names, never one only by its key. After a roll back to a release before 0.53, a save of Crew's project's settings that still holds `check_network` is refused, so the key is taken out first with a PUT of the settings without it. `make check` passed in its check sandbox at CREW-1's merge check (2026-10-22, 8 minutes); from 0.61 it failed there at once, on the sandbox's own `GOPROXY` (BUG-023), until 0.89, shown at 0.89 by a probe made as a check sandbox is (Kata, the large size, Sources behind Crew's own door and its module proxy): 563 seconds of the 30 minutes of `limits.check_timeout_minutes`. Crew's project stays paused until the operator resumes it; the gates since 0.2.29 ran `make check` on the checkout with `crew-ctl gate`.

1. Crew creates a ticket in the Crew project for each improvement that passed its evals, and the operator creates tickets there too: a prompt change, a fix in the orchestrator, a new screen. The daily look for new versions of the CLIs and the tools creates tickets too (12.8).
2. Agents work them through the same stages as any project, in sandboxes. A sandbox never touches the running Crew.
3. Merged tickets collect on `main` of Crew's project until the operator presses Build a release on Versions, or `updates.release_after_tickets` tickets have merged since the last release (since 0.51). The count is of merged tickets; the operator's own pushes count for the button alone. One build runs at a time, and nothing is built when `main` has not moved since the last release. The build takes the newest commit of `main`, except that it stops before the merge of a second improvement, so that one release holds one improvement (10.5); the rest waits for the next release. A release gets the next patch number (0.2.7 to 0.2.8); the button's field takes a minor or a major number instead.
4. **Build once.** The server builds commit C as version V (since 0.51): it exports the commit from Crew's project's canonical repository with `git archive`, and starts a check sandbox for it as it starts every sandbox (13.4, 13.9, with the capacity check and the cleanup of 13.10), of the size build (7.9, since 0.60), as the gate's make check is: a microVM with its own Docker daemon, no socket of the machine, no secret, no token, no login, and the network mode Sources (13.6), whose Go modules come through the server's module proxy (since 0.61). The images leave the sandbox as files, and the server hands them to the updater over its socket; the updater checks their hashes and loads them; it starts no sandbox, and the microVMs of the check in 16.4 steps 3 and 4 (the release's `crew admin` on the scratch copy, the check server, the smoke run, and the browser tests) stay its only ones. The steps are driven by the running release's own script, `deploy/release.sh`, taken from the running release's deploy archive (16.12), whose hash `release.json` carries, never from the machine's files and never from the candidate's copy: the candidate's Dockerfiles, Makefile and tests are code agents wrote, and they run only inside that sandbox. The runtime image is built first, by a command of its own that runs only `image/Dockerfile`, and the server copies it and what it got of `agy` out of the sandbox before the second command builds the other images, so an escape from one of the candidate's other Dockerfiles cannot change the image the live steps give a login to (since 0.52). So a change to the build steps themselves takes two releases: the one that carries it, and the next, which is the first built by it. A microVM cannot start microVMs, so nothing in the sandbox starts one: the smoke microVM and the install test are the updater's (16.4, 16.11). Before the sandbox starts, the server downloads `agy`'s tarball as the commit's `versions.lock` pins it and copies it into the sandbox's home, and the script gives it to the runtime image's build, so the build reaches no storage of the vendor's (12.8, since 0.57); a build whose tarball is not the pin's fails there, with no sandbox started. `crew-ctl build` runs the same script on a checkout, with the tarball it downloads itself; the build by hand stays the way out when no CLI works (16.10). The build's log is on Versions. The result is the release folder, with the deploy archive of 16.12.
5. **Test what was built.** The gate runs on those images, not on a working tree: `make check` and the integration tests in a check sandbox from the exported tree; the candidate's server started in check mode on a scratch copy, with the fake harness, with the selftest and the browser tests against it (16.4); the checks for a clean and reproducible repository (16.12); the install test on a fresh virtual machine (16.11), which the release marks skipped where `updates.install_test` is `off`, and which a gate Crew drives marks skipped with the reason, since it needs a virtual machine started on the machine and runs by `crew-ctl gate` with the operator, without holding the release for it (since 0.52); and the two live steps below. The server drives the gate: `make check` runs in its check sandbox; it asks the updater, over the socket the updater already listens on, for the check mode and the smoke microVM; it runs the two live steps itself, on its own schedule, since it holds the sandboxes, the broker, and the queue, and sends their result to the updater as one request, bound to `release.json`'s hash. The updater writes the one `gate.json`. Until the live result is in, the gate is pending, which is never passed: not for the clock, not for Install, and not for `crew-ctl gate` by hand.
   - **The real ticket** (since 0.51) is one fixed ticket on the fixture project `crew-gate`, which Crew makes and the board does not show: add a small Go function and its test. Its board has In progress, Review, and Test. It runs as a normal run of the running server, in the candidate's runtime image, with the login the broker hands any run, a reviewer on the other family than the builder, and at most 30 turns a run. Since 0.53 it has no budget: its runs' turns and minutes, its fix rounds, and the gate's eight hours bound it. The step passes when the board moves the ticket to Done on its command checks; it fails, with the reason, when the ticket is closed another way, a run of it is stopped, or the eight hours end.
   - **The eval suites** (since 0.51) run only when the release changes what agents see: `baseline/`, `harness/`, `image/`, `internal/cli/`, or `cmd/crew-run/`, and only after the real ticket passed. Their projects are fixed when they begin: each that is not hidden, not archived, and has an active case, by name. Each project is decided before anything of it runs (since 0.52). It is not compared, with why, when it is paused; when it has fewer active cases than `knowledge.evals.min_cases`; when no done suite of it measured a case on its baseline side on the running release; and when the cases that suite measured and that are still active are too few. Otherwise its release suite (9.6) runs each of those cases once, on side `release`: its agent runs start from the candidate's runtime image, and the candidate's six eval files, read from the release's commit in Crew's project, are laid over the baseline, since `baseline/` is built into the server, not into the image. It is compared with that earlier suite by the rule an override is judged by, on the cases that suite measured and the release suite ran, a release run that measured nothing counted as a goal not met for the bound (10.5, since 1.10). One release suite runs at a time, in the `evals` queue behind the operator's own suites; a project whose own suite waits or runs is taken after the others. Worse in any project holds the release until Install, and so does a project whose release suite could not tell because runs of the release measured nothing, counted as goals not met for the bound (10.5, since 1.10): its line says "could not tell". A release suite that stopped keeps the count of its runs that never ran, so it holds the release too, with the same words, while its line says why it stopped. When no project could be compared, the step did not run, and the release waits for Install; when one was and none is worse, the step passes, and the others' reasons are lines of its detail (the operator's choice, 2026-10-20). The step's detail has each project's line, with its numbers or why, cut to 2000 bytes, and is not published; the hold and the notes, which the release's page publishes, name no project and no project's numbers: "the eval suites measured worse in 1 of 2 compared projects; the numbers are on Versions" (the operator's choice, 2026-10-20), and "the eval suites could not tell in 1 projects: runs of the release measured nothing; the numbers are on Versions" (since 1.10). A release whose commit Crew's project does not hold with those six files skips the step. A release of server or UI code only says "no eval: nothing the agents see changed". Since 0.53 the gate's report and `gate.json` carry no cost; a `gate.json` written before with one is still read, and since 0.54 its lines, and those of the gate's row, are shown without the amounts a server before 0.53 wrote into them, while the file and the row stay as written: the real ticket's "for $X" and "spent $X of its $Y", a suite's "($X)", and the hold of other code that named what its runs cost (the operator's choice of report 9). Any other text of a step is left as it is.
   - **When the live steps run.** The candidate's runtime image gets the operator's login and the projects' code only when its code is the running release's. The build decides that, not a list kept by hand: `release.json` records the inputs of the runtime image, which are the hashes of `image/`'s build context, of `versions.lock`, and of every Go file `go list -deps ./cmd/crew-run` names. When they equal the running release's, the live steps run at once, since only text differs, and text is data. A release with a control character in the path of an input is never the same: the hash writes one line for each path, so such a path could make other files hash as the running release's (since 0.52). Such a path is in the diff the press shows, even when its file is the running release's, so the press is offered (since 0.59). Otherwise they wait for a press, Run the live gate, on Versions, which shows that diff first; the gate is pending until then, and Install needs a passed gate, so it is a second press, as for a held release. A gate the server gives up while its `gate.json` waits for the live result (a folder it could not read, a result the updater refused) has its live part written failed by the updater, with the server's reason, so the release is not held pending for good; `crew-ctl gate` can gate it again, and the server takes that new gate up (since 0.59). The press lets the candidate's image run the real ticket on `crew-gate`, and the eval suites' builders, reviewers, and testers in each project the suites run in, with that project's network mode, setup, and read-only GitHub token, as any run of it; the press says so (since 0.52). Such a release is held when its live steps pass: the candidate's image is other code, whose own numbers cannot let it install by itself (from the security review of the eval suites, since 0.52).
   - **Signed out, or at a limit.** When the CLI is signed out, the real ticket's step and the suites are skipped with that reason, and the gate passes with the note. A live step whose runs have waited at a limit (12.7) for six hours is skipped the same way, never failed: a quota day does not fail a release. For the suites that is six hours on end in which their suite's next run waits for a model, which the suite keeps (9.6); the time at a limit does not count toward a bound of their own, 24 hours, after which what is left is skipped too, "they ran out of time", so a queue that does not move does not keep Install refused (since 0.52). Such a release never installs by itself, whatever its kind, and Install says which step did not run. The note is in `gate.json`, and the clock of 16.3 reads it.
6. The app shows the release candidate on Versions: the tickets in it, which are the merges between the last release's commit and this one with their tickets on Crew's project, and the operator's own commits as "from outside" with their first line (since 0.54: "the last release" is the newest release folder whose commit Crew's project holds and is an ancestor, as for the build's plan; a commit of `main`'s own line that a passed merge check names is that ticket, whatever its stage, and any other is from outside, with the commits a merge no ticket made brought in; each list newest first, at most 200, saying when it was cut; a version whose commit Crew's project does not hold says so; a server build's notes are written from the same lists, its tickets and then "From outside", its title Crew's count of them, since an agent's title would name the release on the Install item; the release's page on GitHub shows each line as text, with no link, image, mention, reference, or HTML; what a release with a folder holds is read once, and one whose history cannot be read is a note on its detail); the gate's report with the real ticket and the eval numbers; the kind and the protected paths; the build's log; and `release.json`. The release's notes are written from those tickets, which agents wrote, so each line is screened as a release's title is (one line, control characters removed, 120 characters at most), and it is shown and published as text (since 0.51). The screen names one candidate, whose gate it shows: a gate whose live part runs, whatever its version, since its candidate image holds the agent CLI's login, else the newest, by when it started, of the builds and the gates; its version newer than the running release's and never installed, so a gate `crew-ctl gate` made counts, a failed build stays until a newer one starts, and a release installed once, or rolled back from, is none. `GET /crew/versions/{v}` gives the version's `gate.json` whatever its state, a failed one too, and where the gate's live part is: the real ticket's key and its stage on `crew-gate`, then its step; each project of the suites with its suite's state, what its next run waits for, and its verdict, or why it is not compared; and the suites' step (since 0.52). The candidate's gate is a panel of its own under the three cards, "The gate of V": one line of where the gate is or how it ended; each step with its mark, from `gate.json` once it is there, and before it from the gate's row and the updater's request of that gate; while the live part runs, the real ticket's stage and each project's suite, as text, since `crew-gate` has no screen; what did not run, with why; on a gate that waits, the runtime inputs that differ, each character of a path outside printable ASCII shown as its code point, and Run the live gate; and the build's and `make check`'s logs, collapsed. Every text of the panel is shown without control characters, colours, or characters that reorder text: step details, errors, notes, and project names come in part from the output of code agents wrote. Since 0.54 every text of Versions that comes from outside the app is marked as not the app's own: a release's notes and title, what the updater or a command said, a step's detail, the logs, the paths, the agy pin, and the projects' names; a line that joins the app's words with such a text keeps its own words read. The no-dollar browser check of the gate and of an installed machine reads Versions too (the operator's choice of report 9). A waiting gate whose diff is empty offers no press and says why, from the gate's `noDiff`: the running release cannot be read, a release records no runtime inputs, or a release's recorded hash of its inputs is not theirs; a candidate whose recorded hash is not its inputs' shows no diff whatever its inputs, and the server refuses its press, since the press binds to that hash (since 0.59; before, it always blamed the running release). The press asks once, naming the version and what it lets the candidate's image do, and sends, for that version, the hash of the inputs whose diff it showed as it was opened; a refusal shows the server's words. With no release waiting, the Next release card says only that none waits (since 0.52).

### 16.3 Notice, and what installs by itself

A release candidate that passes the gate becomes a release. Crew then gives notice. What happens next depends on what the release changes. You decided this in 0.29.

| The release changes | What happens |
| --- | --- |
| Only text for agents: Markdown files under `baseline/` and `harness/`, which are prompts, skills, rules, and agent definitions, and none of the protected settings (16.8) | It installs by itself 24 hours after the notice (`updates.install_after_hours`), unless the gate skipped a live step (16.2 step 5, since 0.51) or holds it, because a suite measured worse or the live steps ran in a candidate runtime image of other code than the running release's (since 0.52): then it waits for Install. Install now and Hold are the alternatives. |
| Anything else: the server, the UI, the updater, the scripts, a schema change, what Crew depends on, anything under `image/`, and under `harness/` a hook, a script, a settings file, an MCP configuration, or the model line of an agent file | It waits. The notice says so, and it installs when you press Install. |
| Something that needs a newer machine setup (16.4) | It waits. Install then stops at its first step and shows the one command to run on the machine. |

| Step | What happens |
| --- | --- |
| 1. Release | The gate has passed. The release is named by its content hash, tagged, and published (16.9). |
| 2. Notice | The operator gets a notification and an inbox item: the version, the tickets in it, the gate report, and either the time it will install by itself or that it waits for Install. |
| 3. Wait | 24 hours for a release of text. Until your press for every other release. |
| 4. Install | The updater installs it (16.4). The operator gets news that Crew is now on the new version, or that the check stopped it and nothing changed. |

- **Why code waits.** The server is one program. It holds the Docker socket, the database, and the key to your credentials, so code in any of its files runs with the rights of all of them. A list of protected parts cannot bound that. A press from you can.
- **Which kind a release is** is decided by the running version, from the paths the release changes in the repository, not from which images are built again. A new prompt is built into the server image and a new skill into the runtime image, and both are still text. An agent cannot mark a release as text.
- **Install now** starts the update at once.
- **Hold** keeps a release of text from installing until the operator presses Install. A later release replaces a held one, and gets its own notice.
- **No agent can shorten the wait, lift a hold, or install.** The Crew MCP has no tool for it, and these routes are not reachable from a sandbox's network.
- The updater installs only a release that passed the gate, and only if the files still have the hashes that were tested. The one exception is a build by hand, which only root on the machine can install (16.10).
- **What reaches a release without you.** New versions of the CLIs and the tools (12.8), and improvements to the baseline whose evals are not worse (10.5). A ticket you add to Crew's board is yours. The notice of the release lists every one of them. An improvement can also be taken out of a release that is not installed yet. Its ticket, when it is not Done, is closed with it. When it is Done, in Crew's main but in no installed release, Take it out makes a revert of its ticket, as Crew's own (7.13), and removes the improvement; while the revert is not merged a build is made as always, and every release that holds the improvement's merge and not its revert's is held, at its notice and, for one that waits already, on the next round of the releases before their clock: it waits for Install, with a reason that names the improvement by its number (since 0.55, the operator's answer 3 of report 10: held, not refused, so the operator's other work still builds). A history Crew cannot read holds the release too, and the hold reads the improvement's project from its ticket, so it holds where the server builds nothing or no setting names Crew's project, and one whose Done ticket has no merge recorded holds as unread; the clock reads it again for the release it is about to install. Take it out and the clock take one lock, and the take-out reads the improvement's status again under it before it changes anything, so the clock installs no release with an improvement while it is taken out, and one installed meanwhile is refused with nothing made (round 2 of that review). An improvement in an installed release is measured there and is refused here (10.5); so is one while Crew's project is paused, since a revert is made only in a project that runs, one while a release installs, one whose Done ticket has no merge Crew recorded (the operator can still revert that ticket on the board), and one where the history of an installed release cannot be read (a release by hand of a commit Crew's project does not hold refuses every such take-out, and says which release); a refusal changes nothing (security review of 1863a0e..f8d57b2). A removed improvement no longer stops a build as a second improvement would (16.2 step 3).
- **What this costs you.** A press for most releases. A new version of a CLI changes the runtime image, so each one waits too.
- `updates.auto_install` can be set to `unprotected`, which is the rule before 0.29: every release installs by itself unless it touches a protected part, or the gate skipped a live step (since 0.51), or the gate holds it (since 0.52). Set to `never`, every release waits. Another installation, whose `updates.source_repo` names no repository, takes `never` whatever the setting says (16.12, since 0.69).

There are no signing keys. On one machine that is Crew's alone, a key would protect little: the server already controls Docker on that machine. What matters is that what is installed is exactly what was tested, that a bad release is caught before and after the switch, and that code is installed when you say so. The releases published on GitHub are copies for your own machines (16.9). There is no signing as long as you bring every release to a machine yourself, also to a client's (16.12). If releases ever reach a machine another way, signing comes back.

### 16.4 Updating

The updater is a small program in its own container, `crew-updater`, beside the server. While Crew runs, it is the only thing that replaces a core service. `crew-ctl` starts and stops them at install, at `edit`, and at uninstall (16.11).

| Step | What happens | If it fails |
| --- | --- | --- |
| 1. Ask | The 24 hours of a release have passed, or the operator presses Install now, Update, or Roll back in the app. The server sends a request with a version to the updater, over a socket on the machine that only root and the server's container can open (16.11). | The updater refuses a version that did not pass the gate, that is on hold, or whose files have changed. |
| 2. Load | The updater loads the release's images and checks their hashes. | Nothing has changed. |
| 3. Try the state | The updater writes the candidate's container spec itself, from the installed deploy files and the release's image hashes, never from the candidate's Compose file: no Docker socket, no key file, the scratch network (since 0.51). It dumps the database, without the events of months that have ended: their month files hold them (16.9), and a schema change does not rewrite them. That dump is the snapshot. It is restored into a scratch database in a database container of its own, `crew-db-check`, on a network of its own, with passwords and an ingress secret the updater makes for each check (since 0.48): nothing of the running database's is given to the release that is checked. The release's own `crew admin` reads the snapshot into that copy and applies the release's schema changes to it, one microVM for each command, from a spec the updater writes as it writes the check server's: no other runtime, no capability, a read-only root with a small tmpfs and no volume, the migrate role's secret of the check alone, the one snapshot read only, as a copy the updater makes in the check's own folder of the file it opened, never through a link, and the database's address; it is code agents wrote with a copy of the whole database (since 0.52, from the security review of the first gate's fix and the reviews of that change). The new server is started beside the running one, on it, in a microVM, since it is code agents wrote, never on a runtime that is no microVM's, whatever the server is allowed, and a check server that cannot start there fails the check and says so (since 0.52). A microVM has a network stack of its own, which Docker's name server on the scratch network does not answer, so the updater gives the check server the database's address, and the browser tests' microVM the check server's, as hosts entries, and starts neither when the container it reaches has no address there (since 0.52, from the first gate on dave). It runs in check mode: it answers and reads, it refuses every request that would change something, and it starts no orchestrator, no notifier, no timers, and takes over no sandbox. | Nothing has changed. The running version never stopped. |
| 4. Check | The new server must report healthy. Then a smoke run: the updater starts a microVM from the new runtime image, with no network, in which a command prints an event that the new server stores, and removes it (since 0.52: the server in check mode has no Docker socket). Since 0.53 the smoke microVM is bounded as the restore's is: no capability, no way to gain one, bounds of its own (256 processes, 1 GB), and a read-only root with one tmpfs, `/tmp`, which holds its home and the proof's file; it runs as the user nobody, as before. A release that was installing by itself is put on hold. |
| 5. Switch | New runs are held. The old server stops. The updater applies the schema changes to the real database in one transaction, so they apply fully or not at all. The new server starts. This takes seconds. Sandboxes keep running, and their events wait in their spools. | The transaction is undone, and the old server is started again. |
| 6. Watch | For ten minutes the updater watches the new version's health. | The updater switches back by itself (16.5) and puts the reason in the inbox. |
| 7. Keep | The release is recorded as running. - The check comes before the switch. A version that cannot start, cannot read the stored state, or cannot start a microVM is found while the old version is still running.
- Every step is shown live on the Versions screen, with the updater's own log.
- **The machine's setup.** Docker, Kata, and the firewall are installed by the host setup, not by the updater. A release that needs a newer setup says so. The updater then stops at step 1, and the app shows the one command to run on the machine: `crew-ctl install --upgrade-runtime`. `versions.lock` holds the number of the machine setup, and the record of the install says which one the machine has. This is rare.
- **First install.** On a new machine, `crew-ctl install` installs Docker and Kata, builds or pulls the images, and starts them (16.11). After that, updates come from Crew itself.

### 16.5 Rolling back

| Kind | How |
| --- | --- |
| Automatic | A new version that turns unhealthy in the first ten minutes is switched back by the updater, without the operator. |
| From the app | The Versions screen lists every version with its date, its changes, and its results. Roll back to any kept version starts the same steps as an update, with that version's kept images. Nothing is rebuilt. |
| An improvement that measured worse | Crew takes it out again by itself: back to the release before it, or a new release without it when others were installed since (10.5). The operator gets news of it. |
| When the app cannot be opened | `crew-ctl rollback` on the machine asks the updater directly. The updater does not need the server. |

### 16.6 Stored state across versions

The stored state is the database. A roll back is only safe if the older version can read what the newer one wrote.

- The database has a schema number. A release says which numbers it can read. Since 0.48 each schema step says in its header whether the version before it reads the result, and `release.json` names, as `readBy`, the lowest schema whose server still reads the database it leaves.
- A change to the schema is first tried on a copy, in step 3 of every update. A change that fails never reaches the real database.
- A change to the format is made in two releases. The first adds the new form and keeps reading the old one. The second removes the old form. So the previous version always runs on the current state, and a roll back by one version needs no restore.
- A roll back across a change the older version cannot read restores the snapshot from step 3. What was written after it is lost. For the automatic switch back that is the minutes of the check and of the watch. A roll back from the app across such a change, days later, would lose everything written since: Crew does not do it by itself. It shows what would be lost, and the operator types the version's name to go on. Code is in git and is not touched. The events of sandboxes that are still running are read again from their spools. Such a release is a protected one and waits for Install (16.8).
- The scratch database is removed after the update. The snapshot is kept with the release.

### 16.7 Running work during an update

- Running sandboxes are not stopped. Each run writes its events to a spool in its own home (12.4), so the new server picks every run up at the last event that was stored.
- The orchestrator starts no new run from the switch until the new server is up. That is seconds, not the length of the check.
- **Every new microVM uses the new image by itself.** From the switch on, each sandbox that starts is made from the running version's runtime image: runs, the project terminal the next time it is opened, checks, and Setup. Nothing has to be changed per project.
- A sandbox that is already running keeps the image it started with until it ends. The Versions screen shows how many are still on the old one.

### 16.9 Releases, and backups

A release is more than a folder on the machine. It is published, so there is a clear list of releases outside Crew, and no release is lost if the machine's disk dies.

| What | Where it goes | When |
| --- | --- | --- |
| The source | The tag `vX.Y.Z` in `kesokaj/crew` | When the release has passed the gate, before the notice |
| The release | A release on GitHub for that tag, with notes written from the tickets in it and the gate report, screened first, since agents wrote the tickets (16.2) | The same moment |
| The images | The private container registry of the repository on GitHub, under the same version | The same moment |
| Crew's database: one dump, without the events of months that have ended | One tar.gz file per day in the backup folder on the machine | After every update, and once a day |
| The events of each month that has ended | One file per month in the same folder, kept for good | Once, when the month has ended |
| The repositories of projects that have no remote | The same tar.gz file | Once a day |
| The data directories of hosted projects | The same tar.gz file | Once a day |

- No signing keys are used. The tag is made through GitHub's API with `gh`'s login, at the release's commit (since 0.48), and a tag is never moved.
- The tag, the release page, and the images need `gh`. Crew gives Docker the login `gh` holds for each push to GitHub's registry, and writes it nowhere. Without `gh`, a release is the folder on the machine until `gh` is signed in, and a checkout of the commit with `crew-ctl install --build` builds it again.
- The repository and its registry are private, and stay private. A release is visible to your account only.
- Publishing is a copy, not the way an update arrives on the main installation. An update still installs the release folder on the machine (16.4). On another installation the release folder is first brought there (16.12).
- If the copy cannot be made, the release still installs. The Versions screen shows what is not yet copied, and Crew tries again. With `updates.publish` off nothing is copied, and Versions says so on the line of each release that passed its gate, "not copied to GitHub: copying is off", never that it is being copied (since 0.53; on dave, with publish off, every such line said "being copied to GitHub").
- **Backups are local.** You decided this in 0.21 and again in 0.26. The last 14 daily files are kept in `/var/lib/crew/backups`. They protect against a bad update, a mistake, and a deleted project.
- **Trajectories are backed up by month.** They are kept for good, so they are the largest part of the database. A day's file holds a dump of everything except the events of months that have ended. Each ended month of events is dumped once, into its own file in the same folder, and that file is kept for good. When you delete a project or a conversation, the files of the months it touched are written again without it. So a day's file stays small, and 14 of them do not hold the same trajectories 14 times.
- **A dead disk costs more than before 0.25.** The database and its backups are on the same disk. If it dies, everything in the database is lost: tickets, records, conversations, and trajectories. The code of projects with a remote survives on GitHub, and so do the releases. Before 0.25 the tickets and records of such a project were also in its repository. You decided to keep the backups on dave for now. Copying each day's file somewhere else stays one setting, `updates.backup_copy_to`.
- **A new main machine,** when dave is replaced. A checkout of the release's tag and `crew-ctl install --build` bring Crew up at that version. With the release's card and `--registry-token-file` the images are pulled instead of built (16.12). Then `crew-ctl restore` reads a backup file back. Projects with a remote come from it.
- A backup file holds the credentials only in encrypted form, and the key is not in it (15.3). After a restore on a new machine, the operator signs in again in Setup. The work folders of conversations are sealed with that key too, so without the key file they are lost, and each conversation's next sandbox starts without its folder (11.8, since 0.76). So are the CLI's own files of every run and conversation (since 0.78): without the key file none is put back, and each is continued rebuilt from its turns (12.10). Backups made before 0.78 hold them in plain text.

### 16.11 Install, update, and uninstall

Installing Crew, updating it, and taking it away again are features, and they must work on a fresh machine (R198). One program does all three: `crew-ctl`.

**What `crew-ctl` is.** A shell script, `deploy/crew-ctl`, as styrman-crew's `styrman-ctl` is. It must run on a machine that has nothing yet, so it needs only a shell. It does the machine's part: checking, installing, starting, stopping, and removing. It does not read or write Crew's data itself. That is done by the server's own program, `crew admin`, which `crew-ctl` runs inside the server's container, or in a container of the server image that lives for one command when the server is down.

- Install copies `crew-ctl` to `/usr/local/sbin/`, and the files it needs to `/usr/local/lib/crew/`: the host setup, the Kata configuration, the firewall, the units, the Compose file, and `versions.lock`. After that it does not need the checkout.
- **An update does not replace them** (since 0.51). It replaces the containers, and the machine's part is root's. Install writes the hash of each file it copied into its record, by its path in the repository: in `install.json`, for the operator, and in `deploy-files.json` in the releases folder, which the server reads (since 0.55). Every run of `crew-ctl` compares the files in place with the deploy archive of the running release (16.12), and Versions compares the record with it, in the row `crew-ctl` of Running now, which says "as install recorded them": the server cannot read root's files, so a file changed in place since is `crew-ctl`'s to tell. When they differ, or nothing was recorded, one line says so and gives the command to run as root: `crew-ctl`'s line names its own `install --deploy-files`; Versions' command checks the archive's hash against `release.json` with `sha256sum -c`, unpacks the archive's `crew-ctl`, checks its hash against the archive's, and only then runs it with `install --deploy-files`. `install --deploy-files` reads the archive once, at most 64 MiB, and checks the very bytes it unpacks: the archive against `release.json`, `release.json` against its folder's name and against a `gate.json` of its version that passed, whose live part is not pending or failed; with no gate only the running release, built by hand. It unpacks only the deploy files' own names (the fixed list, and one name of letters, digits, dots, dashes and underscores under `deploy/db`, `deploy/lib`, `deploy/firewall`, which a release's archive may hold no other of), regular files of at most 16 MiB, into a folder of `mktemp`, checks every file the copy names is there, puts them in place, records them, and changes nothing else, except that the running release's files make `install.json` name that release as installed (since 0.78: an install of a build by hand, as `install --upgrade-runtime`, left its own version there, and an update leaves it; an install that stopped half way stays unmarked, for `doctor` to say); an archive or a gate that does not check is refused, and is offered to no one. Every Python `crew-ctl` runs is isolated (`python3 -I`), its own and that of the scripts it runs as root, so nothing of the caller's folder is imported as root (reviews of 864fb57..97382bc, two rounds). After a roll back the running release is the one rolled back to, and its files are the ones offered. The update is not held for any of it. On dave in M15, a `crew-ctl` older than the releases refused `build --title`. Since an update starts the containers from the Compose file in place, a release that changes how Compose starts a core service has its deploy files put in place before its update, by `install --deploy-files --version X.Y.Z` once its gate passed, and the update starts the service with them: since 0.83 `crew-server` and `crew-caddy` start with forwarding off (13.6), and `doctor` fails while either runs without it, with that command. Only `doctor` checks it, so an install that would start them again is not refused for it.
- `crew admin` is reached through Docker on the machine, never over a network. Root on the machine can already read the key file, so this is not a third door (20.3).

**Getting it onto the machine.**

| Which machine | How |
| --- | --- |
| Your main machine, dave | You put a checkout on the machine yourself: a clone with your own git access, or a copy. Then `sudo deploy/crew-ctl install --build` builds the images from that checkout, on the machine. The installer asks for no GitHub credential and stores none. This is also the path of the first install, when no release exists yet. |
| Another machine: your own, or a client's you choose | With the card of a release, which you copy there, and `--registry-token-file`, which pulls its images from your private registry, with a token that is used once and not kept: `sudo deploy/crew-ctl install --from <card> --registry <host/path> --registry-token-file <file>`, run from the card's unpacked deploy archive. That machine holds no source of Crew, only images (16.12). |

- A checkout at a tag builds that version. A checkout at no tag builds `0.0.0-dev.<commit>`, which is a full name of its own and never a moving tag.
- A first install also writes a release folder with its `release.json`, so the updater later has a version to go back to (16.4).
- `crew-ctl release pull` and `crew-ctl release import` bring a later release to such a machine (16.12).
- `--registry-token-file` lets an install pull the images of a private registry, with a token that is used once and not kept. Its one line is `USER:TOKEN`, as `docker login` takes them. Since 0.70 the file is root's or the user's of `sudo`, no link, and no one else may read it (0600); `crew-ctl` refuses another, and checks and reads it through one open of it. It is for a second machine of your own, or a client's.

**The verbs.**

| Verb | What it does |
| --- | --- |
| `doctor` | Checks the machine and the answers, and changes nothing. It also runs in `install` and `update`. |
| `install` | Brings a fresh machine to a running Crew. Run again, it repairs. From a newer checkout, it updates (until M14). |
| `status` | What is installed, at which version, and what is running. Ends with 0 when all is well, 1 when something is wrong, and 2 when nothing is installed. |
| `update`, `rollback` | Asks the updater for a version, the same way the app does (16.4, 16.5). From M14. |
| `edit` | Changes a value in `/etc/crew/crew.env`, checks it, and starts again what uses it |
| `uninstall` | Takes Crew away, at one of three levels |
| `logs` | The logs of the server, the ingress, the database, and the updater |
| `build` | Builds a release folder from a checkout (16.10), with `--version X.Y.Z`. From M14. Since 0.51 it runs `deploy/release.sh`, the script the updater runs for a release Crew builds (16.2). With `--out DIR` (since 0.69) it builds into a folder of root's, of whoever ran sudo, or of the caller, as `release card` writes, which this machine's updater and Versions do not read: the install test's phase `second` builds another machine's releases so. |
| `gate` | Runs the gate on a release folder and writes its `gate.json` (16.2). From M14. From M16 the updater runs the same steps on a release Crew builds; the verb stays for a build by hand. |
| `install --deploy-files` | Puts `crew-ctl` and its files of the running release, or of `--version`, in place from its deploy archive, once the archive checks against `release.json` and `release.json` against a gate that passed (a release by hand only when it runs), and records them; with the running release's files, `install.json` names that release (since 0.78); changes nothing else. Since 0.55. |
| `restart-if-quiet` | The restart timer's (16.10): asks `crew admin restart-check` whether the machine may restart for security updates, and restarts it on a yes. Since 0.67. |
| `release card` | `release card X.Y.Z [--out DIR]` writes the card of a release of this machine: its folder without the images, to copy to another machine (16.12). Since 0.69. |
| `release pull`, `release import` | Brings a release of your main installation to another machine: `release pull <card> --registry <host/path> --registry-token-file <file>` pulls its images from your private registry with a token that is used once, and `release import <folder>` takes a whole folder that was copied. The images are checked against `release.json`, and the release then waits for Install (16.12). From M14; the card since 0.69. |

| Passed on to `crew admin` | What it does |
| --- | --- |
| `migrate` | Applies the numbered changes of the schema that are not applied yet |
| `backup`, `restore` | A backup now, and a backup read back (16.9) |
| `settings export`, `settings import` | Both sets of settings as files (14.3) |
| `project export`, `project import` | A project as a folder of files (6.2) |
| `db shell` | `psql` with the role that can only read (15.3) |
| `pause`, `resume` | Pause all, and Resume, when the app cannot be opened (7.9) |
| `selftest` | Runs one ticket on the fixture project with the fake harness, and says whether it reached Done |
| `proof` | Writes a row as the server's role and reads it back: the database part of install's proof. From M3 also `crew admin proof event`, in the server's container: a microVM prints an event with `crew-run proof`, and the server stores it and reads it back |

- Every verb takes `--dry-run`, which prints each command it would run and runs none. `status` and `doctor` take `--json`, for a result a program can read. styrman-crew's script has that for `status` only, so the rest is new.
- `--yes` takes the defaults. `--confirm <word>` gives the word a destructive step asks for, so that a script can run it.
- Every step is safe to repeat: it looks first, and changes only what differs.

**What it gathers first.** Everything the installer needs is asked for before anything is changed: in a `.env` file given with `--env-file`, from the file an earlier install left in `/etc/crew/`, or one question at a time when the installer starts. The repository holds `.env.example`, which explains every key.

| Key | What it is | Must be given |
| --- | --- | --- |
| `CREW_HOSTNAME` | The address Crew is opened at, such as `crew.example.com`. The sign-in page of the ingress is at `auth.` before it, so both names must point at the machine. | Yes |
| `CREW_APPS_DOMAIN` | The domain hosted projects get their addresses under. A separate domain or sibling subdomain from the one above, such as `apps.example.com` beside `crew.example.com` (19.4): crew-ctl, the server, and the ingress refuse it and host nothing while it is empty, Crew's own address, or one of the two is under the other; the ingress no longer takes Crew's address when it is empty. The Google sign-in client then lists a second redirect address, for the apps domain's portal (19.4). | Only for hosting |
| `CREW_ADMIN_EMAIL` | The Google account that may sign in. It is also the contact for certificates. | Yes |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | The Google sign-in client for the ingress. You create it once in Google's console, with the redirect address `https://auth.<CREW_HOSTNAME>/oauth2/google/authorization-code-callback`, which `.env.example` also gives. | Yes |
| `CLOUDFLARE_API_TOKEN` | Lets the ingress write the DNS records and get certificates. Without it you set the DNS records yourself, and hosted projects get no wildcard certificate. | No |
| `CREW_TLS` | Where certificates come from: `acme`, `staging` for the test certificates of the same service, or `internal` for certificates the ingress makes itself. `internal` is for a test machine: the names and the sign-in client are then not checked. | No. It is `acme`. |
| `CREW_DATA_DIR`, `CREW_TIMEZONE` | Where the data is kept, and the machine's time zone. They default to `/var/lib/crew` and to the machine's own. | No |
| `CREW_SOURCE_REPO` | The repository this installation builds Crew from and pushes its own changes to, as `owner/name`. It is only the first value of a setting. Setup asks for it, and checks it with a push of an empty branch once the SSH key exists (16.12). | No |
| `CREW_ALLOW_IP_FORWARD` | Empty, or `1`: the server then starts sandboxes even when its network namespace forwards between bridges or cannot be read (13.6). Never asked; set it with `crew-ctl edit`, and `doctor` warns while it is `1` (since 0.85). | No |

- **One place.** These values are in `/etc/crew/crew.env` and nowhere else. They are changed with `crew-ctl edit`. The app shows them and cannot change them. The settings in the database have no copy of them (14.1).
- **Generated, never asked:** the key file `/etc/crew/secret.key`, and in `/etc/crew/secrets/` the database passwords, the secret between the ingress and the server, and the key that signs sessions.
- **Not asked here:** the git identity, the SSH key, `gh`, the GitHub App, gcloud, `agy`, and the mail account. They are logins, and they are set up in Setup, the first screen of the app (12.6).

**Where things are.**

| Place | What | Kept by uninstall level 2 |
| --- | --- | --- |
| `/etc/crew/` | `crew.env`, `secret.key`, `secrets/`, and `install.json`. Root only. | Yes |
| `CREW_DATA_DIR`, by default `/var/lib/crew/` | The files of the database, the repositories, the homes of running sandboxes, the release folders, a build's files until the updater loads them, and the backups | Yes |
| `/usr/local/sbin/crew-ctl`, `/usr/local/lib/crew/` | The installer and its files | `crew-ctl` only |
| Docker | Crew's containers, images, and networks | No |

- **Who runs it.** Install creates a system user, `crew`, with no login. It owns the data folder, and the server's container runs as it, with the group of the Docker socket. No account of a person is put into the `docker` group.
- **Who the agent is.** In every sandbox the user is `agent`, with the user id 1000 and the home `/home/agent`. It is fixed in the image. styrman-crew uses the operator's own account name for both, so that name is in every path and every recording there.

**What `doctor` checks.** It finds out by itself which case it is in: a fresh machine, a repair of an installation that is there, or an update. In a repair and an update, Crew's own containers, ports, units, and firewall chains are expected. Run alone with no answers, it checks the machine and says that the answers were skipped.

| Check | Fails when |
| --- | --- |
| The system | It is not Debian or Ubuntu on AMD64, or it is older than what Docker and Kata support |
| Virtualization | `/dev/kvm` is missing: the machine is not bare metal and has no nested virtualization |
| Room | Fewer than 8 cores, 32 GB of memory, or 200 GB of free disk. It warns below 16 cores and 64 GB. |
| The network | Ports 80 and 443 are taken by something that is not Crew, the machine cannot reach GitHub, Docker's and Kata's downloads, or Google, or its clock is off |
| The names | `CREW_HOSTNAME`, `auth.` before it, or (when `CREW_APPS_DOMAIN` is set) `auth.<CREW_APPS_DOMAIN>` does not point at this machine, and there is no DNS token to make it so |
| The answers | A key is missing or has the wrong form, the sign-in client is refused by Google, or the DNS token cannot write to the zone |
| What is already there | Running parts of styrman-crew: its containers, its units, or its firewall chains. An installation of Crew with another data folder. Firewall rules that would clash. |
| Docker and Kata | Docker is at another major version than `versions.lock` names. The message gives the one command that replaces it: `crew-ctl install --upgrade-runtime`. A Kata older than `versions.lock` is no failure: install moves it, beside the one that runs (13.2, since 0.68). |

- **Warnings, not failures:** what styrman-crew's own uninstall leaves behind, which is its data folder and two small files. A Docker at another version of the same major line, and a Kata newer than `versions.lock`, which are left as they are. 3.31's `/opt/kata` once nothing runs from it, when Crew did not install it: it is the operator's to remove (since 0.68).
- **The sign-in client** is checked by asking Google for a token with a code that is made up, and then asking Google's sign-in page (`https://accounts.google.com/o/oauth2/v2/auth`) with each redirect address (`https://auth.<CREW_HOSTNAME>/oauth2/google/authorization-code-callback`, and when `CREW_APPS_DOMAIN` is set `https://auth.<CREW_APPS_DOMAIN>/oauth2/google/authorization-code-callback`). The answer that the client is unknown, or `redirect_uri_mismatch` for a redirect address, fails (naming the missing redirect address). The answer that the code is wrong and the redirect addresses are accepted passes. No answer is a warning. The question for the client's id, doctor's line for the client, and install's last lines also name the exact redirect addresses the client lists.

**What `install` does,** in this order. Each step is recorded in `/etc/crew/install.json`, with whether Crew put the thing there or found it. An entry that says Crew installed something is never changed to "found" by a later install.

1. Gathers the answers. Nothing is written yet.
2. Runs `doctor` on the machine and the answers, and stops on a failure.
3. Writes `/etc/crew/crew.env`, and creates the user `crew`.
4. Installs Docker at the fixed version, unless it is there (13.2).
5. Installs Kata at its fixed version, checked by checksum, beside the one that runs, merges Docker's settings, and switches the runtime `mvm` to it after its proof (13.2, since 0.68). Cloud Hypervisor is inside Kata's archive, so one checksum covers both.
6. Installs the firewall with its units, and tests it.
7. Makes the data folders, the key file, and the generated secrets. It makes only what is missing: a key file or a password that is there is never replaced.
8. Builds the images from the checkout, or pulls the images of the release. Only then does it copy `crew-ctl` and its files into place: a build that fails leaves them those of the release that runs, which its updater reads; the install file and what steps 3 to 7 made are written already (since 0.52, from the install of 0.2.12 on dave).
9. Starts the database, applies the schema with `crew admin migrate`, and starts the server, the ingress, and the updater.
10. Proves it.
11. Prints the address. Setup is the first screen there.

`install.json` also records the data folder, the user, the packages the host setup added, the kernel setting, the three small files it put under systemd, the restart timer with its service and the two files of the security updates' settings (since 0.67, apart from the three, as R118 names them), the keys it added to Docker's settings, and the number of the machine setup.

**What install does at each milestone.** The updater and the Crew MCP come later in the build, so the proof grows with it.

| From | Install | Its proof |
| --- | --- | --- |
| M1 | Steps 1 to 9, with `--build` only. It starts the database, the first server, and the ingress. There is no updater yet. | One microVM starts and has Kata's own kernel. The firewall test passes from inside it. The server answers behind the ingress. A row is written to the database and read back. |
| M3 | The same | Also: an event that a microVM prints is stored |
| M6 | The same | Also: the microVM reaches the Crew MCP. This is what "healthy" meant in 16.8; since 0.52 the smoke run of a release in check mode has no network, and does not test it (a known limit). |
| M14 | Also the updater, release folders, pulling images, `update`, `rollback`, and `build` | The same |

**Update.**

- **Until the updater exists (M14):** `sudo deploy/crew-ctl install --build` from a newer checkout. It takes a dump of the database first, builds the images, applies the schema, and starts the new containers. There is no way back except that dump.
- **From M14:** `crew-ctl update` asks the updater for the newest release, or for the one named with `--version`. It is the same path as Install in the app, with the same check before the switch and the same switch back (16.4). `crew-ctl rollback` goes back to a kept version. Both work when the app cannot be opened.
- **How the updater is asked.** It listens on a socket, `/run/crew/updater.sock`, which only root and the server's container can open. It takes install a version, say where it is, and stop; since 0.51 also load the images a build made, run the check mode and the smoke microVM for a release folder, and take the live steps' result, after which it writes `gate.json` (16.2). The table of update requests in the database is its log. `crew-ctl` uses the same socket, so it needs no server. One updater runs at a time (since 0.53): as it starts it takes a lock beside its socket, `/run/crew/updater.lock`, before it reads a request or touches the socket, and a second one, also one started by `docker exec` in the updater's container, stops there. The folder is root's alone and the lock root's own regular file, 0600, never a link, so the user crew, which owns the data folder, can neither hold it nor put another in its place (from the security review of 0.53, two rounds). `crew-ctl uninstall` takes it out with the socket. On dave a second one took the socket over and removed it when it was stopped, and its start would have recorded a running request as stopped. The kernel lets go of the lock when the updater ends, and the server stops the old updater before it starts a new one (16.8). The updater also refuses `CREW_UID` or `CREW_GID` 0: those ids own the snapshots, and every microVM of the gate runs as them.
- **A newer machine setup.** `versions.lock` holds a number for the machine setup, and `install.json` the number this machine has. `crew-ctl install --upgrade-runtime` brings Docker, Kata, and the firewall to the versions of the release (16.4).

**Uninstall.** It prints the exact plan first, and asks for a word before it starts.

| Level | The word | Removes | Keeps |
| --- | --- | --- | --- |
| 1. Stop | `stop` | Nothing. It stops the services and every sandbox, and switches the units off. | Everything |
| 2. Remove Crew | `uninstall` | The services, every sandbox and its network, the firewall rules, the units, the images, and the installer's files | The data folder with the database and the backups, everything in `/etc/crew/`, `crew-ctl` itself, Docker, and Kata |
| 3. Remove everything of Crew | The machine's name | Level 2, and then the data folder, the backups, `/etc/crew/`, the user `crew`, and `crew-ctl`. It cannot be undone. | Docker and Kata |

- **An install after level 2** finds its answers, its key file, and its passwords in `/etc/crew/`, so it opens the kept database again.
- `--with-runtime` at level 3 also removes Docker and Kata, and takes Crew's lines out of Docker's settings again. It does so only for what `install.json` says Crew installed: every folder of Kata the host setup unpacked, which it lists (`kata_dirs`, since 0.68), and 3.31's `/opt/kata` with its shim wrapper when Crew installed that. `/etc/crew/` is removed last, after `install.json` was read.
- Uninstall takes out what install put in, and nothing else. After level 3 with `--with-runtime`, `doctor` finds the machine as a fresh one.
- **What is not on the machine** is listed at the end, because uninstall does not touch it: the repositories and the GitHub App on GitHub, the sign-in client at Google, and the DNS records. The DNS records that the ingress wrote are removed if you say yes.

**Tested like a feature.** The install test brings Crew up on a fresh virtual machine with nested virtualization. The virtual machine is started on dave itself, from a Debian or Ubuntu cloud image, as an ordinary container that holds QEMU and is given `/dev/kvm`. The updater starts it, because the updater holds the Docker socket. Until the updater exists (M14), the builder starts the same container with `make install-test`. So it needs no cloud account. Kata inside that virtual machine needs nested virtualization, which the kernel of a bare-metal machine has switched on by default. `doctor` reads it. The test runs `crew-ctl selftest`, changes one value with `edit`, takes a backup and restores it, updates, rolls back, uninstalls at each level, installs again on the kept data after level 2, checks that nothing is left after level 3, and installs again (section 22).

- **It needs nothing of yours.** The test machine uses `CREW_TLS=internal`, so it needs no DNS name and no sign-in client. `selftest` uses the fake harness, so no login of a CLI leaves your machine, and nobody signs in through a browser. The real ticket on each CLI runs in the gate on the machine itself (16.2).
- **"Nothing is left"** means: `doctor` reports a fresh machine, and none of a fixed list is there: Crew's paths, units, firewall chains, networks, images, and its user.
- **Where the test machine comes from** is a setting of the installation, `updates.install_test`. `local` is the default: the virtual machine on dave. `off` skips the test, and the release says so; a gate that failed before the test, or could not read the setting, says that instead (since 0.59). A gate Crew drives, not `crew-ctl gate`, does not run it either: the release says so, and is not held for it (since 0.52). A machine in a cloud is a third way that is not built now: styrman-crew has scripts that create one in Google Cloud, and they are not copied.
- The paths `crew-ctl` writes to can be pointed elsewhere, so most of it is also tested without root, with `make check`, as in styrman-crew.
- The server, the ingress, the database, and the updater write their own logs through Docker, with size limits. `crew-ctl logs` shows them when the app is down.
- After a snapshot or a backup is restored, every session and every personal token is ended, and you sign in again. What was taken away after the snapshot is not given back by a restore.

### 16.12 Open-source, reproducible, and clean

Crew originally considered public release in 0.30, deferred publication in 0.31, and ships as a public Apache-2.0 open-source repository (`LICENSE`, `THIRD_PARTY.md`) at design version 2.01. Every guarantee designed so Crew installs reproducibly on any operator's machine and cleanly moves finished releases onto a second machine without source checkouts holds.

**Reproducible.**

| What | How it is fixed |
| --- | --- |
| Docker, Kata with Cloud Hypervisor, PostgreSQL, the ingress, Go, Node, and the base images | One file at the root of the repository, `versions.lock`. It has `KEY=VALUE` lines that a shell, Docker Compose, and an image build can all read, each with a version and its checksum or image hash. The installer and the image builds read it. |
| Places that must name a version themselves | A tool insists on some: the `go` line of `go.mod`, the default of an argument in a Dockerfile, the Node version file. They are on a fixed list, and `make check` fails when one of them differs from `versions.lock`. |
| Go and TypeScript packages | Their lock files. A build that would change a lock file fails. |
| System packages and tools in the images | The version `versions.lock` names, where the package source lets a version be asked for, and the checksum it names where it names one, which the build checks before it installs: a tool's archive by its sha256, `agy` by its sha512, and since 0.82 `chrome-devtools-mcp`'s tarball by its npm integrity. Where the source lets no version be asked for, the release records what it got. |
| What cannot be fixed in advance | Where an upstream apt repo (`gh` / `RUNTIME_GH_VERSION`, Debian Chromium/Python) drops old versions after an upstream release, bump the pin in `versions.lock` (`deploy/host-setup.sh` verifies `DOCKER_KEY_FINGERPRINT` before configuring Docker's apt source); `agy` is pinned by its tarball and checksum since 0.56 (12.8). Each release records exact installed package versions in `release.json`, and the built images are kept. |
| The build | Takes nothing from the machine it runs on, and needs no token. |
| A release | Can be built again from its tag with `crew-ctl build`, and the result lists the same versions. It is not promised to be the same byte for byte. |

- **Initial reference values** of `versions.lock` started from what `styrman-crew` ran at `5c9e6fb` (checked against the author's host in the spike, section 24, item 63), then updated to Go 1.27+, Docker 29+, Kata 4.x, and pinned OCI digests.
- `versions.lock` also holds `MACHINE_SETUP`, the number of the machine setup (16.4).
- The ticket of the daily look changes `versions.lock` and the places on the list together, and `make check` holds them in step (12.8, since 0.51).
- Docker CE itself comes from Docker's apt repository after `deploy/host-setup.sh` verifies `DOCKER_KEY_FINGERPRINT` and pins `DOCKER_VERSION`.

**Clean.**

- **No secret or personal data, ever.** Nothing secret is written into the repository. `make check` (`tools/check-clean.py`) and the gate scan for secret filenames, built binaries, token shapes, personal email domains, and workstation `/home/<user>` paths even on a fresh public clone without `spike/raw/scrub-values.txt`, and the git endpoint refuses a push to Crew's own project that holds a secret.
- **What differs between machines is not in the code.** The address, the admin email, the sign-in client, and the DNS token come from `/etc/crew/crew.env` (16.11). The same code installs on any supported Debian/Ubuntu machine.
- **Module and account conventions.** The Go modules keep `github.com/kesokaj/crew` and `github.com/kesokaj/crew/ingress`. Inside every sandbox the user is `agent`, and on the host the system user is `crew`, so no person's account appears in runtime paths (16.11).
- **Recordings are scrubbed of secrets.** Any CLI recording saved under `testdata/` passes through `spike/scrub.py` first (`section 24, item 62`).
- **A clean start.** Adapted components from `styrman-crew` and `styrman-harness` came in as files without prior commit history, and `THIRD_PARTY.md` records provenance alongside Crew's Apache-2.0 license grant and all third-party Go/npm/Caddy/Playwright/skill licenses.
- **Nothing of an installation.** Tickets, records, settings, and credentials are in the database, never in the repository (6.2).
- **Apache-2.0 source, operator-private runtime images.** The source repository ships under the root `LICENSE` (Apache-2.0). Built runtime images (which install vendor `agy` binaries) are built locally (`install --build` / `build`) or pushed only to the operator's own private registry (`12.6`, `16.12`, register `E18`).
- **These documents** stay in `docs/plan/` of the public repository for architectural transparency.
- **No reporting home.** Crew sends nothing about an installation to anyone (outside the optional Cloudflare public-IP check when updating dynamic DNS records).

**Other installations.** You can install Crew on additional Linux hosts with Docker and Kata (your own machines, or machines you operate). Because every component runs in containers, each secondary host runs the same pinned Compose stack without checking out source code:

| | Primary build host | Secondary host (no checkout) |
| --- | --- | --- |
| Gets Crew | From a checkout, built on the machine in containers (`install --build` / `build`, 16.11) | From a finished release of your primary host: images pulled from your private registry (`install --from <card>`, `release pull`) or imported from a copied release folder (`release import`). No source checkout is required. |
| Makes releases of Crew, and changes its code | Optional (`updates.source_repo`, e.g. `your-org/crew`, 16.2) | No. `updates.source_repo` stays empty, so there is no Crew self-hosting board, gate, or release build there. |
| Updates | Releases built locally (16.3) | Releases you deliver to it (below). Every release waits for `Install` because a secondary host holds no source tree to separate text from code. |
| Improvements | Ship in its releases (10.5) | None are generated there; signals remain local to that installation. |
| Data, projects, sign-ins, settings | Its own (`/etc/crew` + `/var/lib/crew`) | Its own. Nothing is shared across installations (`12.6`). |

**How a release reaches another installation.**

1. On the primary build host, a release is a directory holding its image archives, `release.json` (the SHA-256 of every image file and config digest of every image), `gate.json` (16.4), and a compact deploy archive (`crew-ctl`, host setup scripts, Kata config, firewall rules, systemd units, Compose file, and `versions.lock` — no source code). `crew-ctl release card <version>` exports the lightweight card (the metadata and deploy archive without the multi-gigabyte image tars).
2. For a first install on a secondary host, copy the release card there, unpack its deploy archive, and run `sudo deploy/crew-ctl install --from <card> --registry <host/path> --registry-token-file <file>`, which installs Docker and Kata and pulls the images. For later updates, either pull via a new card (`sudo crew-ctl release pull <card> --registry <host/path> --registry-token-file <file>`) or import an offline folder (`sudo crew-ctl release import <folder>`). The token file is read once into an ephemeral `mktemp` Docker config in `/run` that is removed immediately after the pull and never printed.
3. Each image is verified against `release.json` before use. A pull restricts the card to a release's five components and tags, resolves `<host/path>/<name>:<version>` with the one-shot registry login, walks an OCI index to the single unambiguous `linux/amd64` manifest (rejecting duplicate or variant-ambiguous entries), verifies that its config digest matches `release.json`, pulls by immutable manifest digest, tags locally without clobbering an existing mismatched image, and writes `pulled.json`. `postgres` is pulled from Docker Hub by the index digest pinned in the card's `versions.lock`. Any refusal rolls back tags created during that pull. `release card` refuses to write into world-writable unsticky directories.
   - **Why the config digest** (since 0.69; M17's plan D48). An image ID differs between Docker's classic image store and the containerd image store (which fresh Docker 29 uses for manifest-digest pulls vs archive loads). The config digest is identical in both, so `release.json` records the config digest and the updater validates against either store representation.
4. The verified release appears in **Versions** with the gate report from the primary build host and waits for `Install`. The updater performs the same side-by-side health verification before switching and rolls back automatically on failure (16.4).
5. Verification and trust model: the gate ran on the primary build host before the card was exported, and `release.json` pins every image content/config digest. Crew therefore omits an online signing key service and treats the operator-delivered card + private registry digests as the root of trust (`16.3`).

- Each installation generates its own `secret.key` and credentials under `/etc/crew/`. Backups cannot be decrypted on another host without its key.
- CLI sign-in ownership on secondary hosts is documented in section 12.6 (each machine runs its own Setup and holds its own accounts).
