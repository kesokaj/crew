## 20. Web UI

The UI has one purpose above the others: the operator can always see what the agents are doing, and why.

**The top bar.** The logo with Crew's version beside it on the left (and on screens narrower than `640px`, a menu button that opens the slide-over navigation drawer, since 1.39). On the right: the `Cmd+K` / `Ctrl+K` command palette trigger (`Jump to…`, indexing projects, tickets, sandboxes, and screens, since 1.39), active tickets and lead slots, running sandboxes (`Sandboxes`, opening `/sandboxes`), and the inbox. The limits of the subscriptions are not here and not on the front page. They are on the Agent CLIs screen, and a limit that stops work is an alert.

### 20.3 Signing in to Crew

Crew can be reached from the internet, so a session has limits (R173).

| | |
| --- | --- |
| A session | Lasts 30 days on a device, behind the Google sign-in of the ingress and the admin email. styrman-crew's ingress gives 8 hours and keeps no list, so sessions, the list of devices, signing out, and the fresh sign-in are new code in Crew's server. How it is built (since 0.66, M17): the token the ingress's portal issues, and the cookie that holds it, last 30 days. On Crew's route the ingress passes the token's issued-at time as `X-Crew-Auth-Time`, in decimal seconds, and its id as `X-Crew-Session`; every route removes a client's copies first, since the plugin sets a header only when its claim is there. It is the one portal's lifetime, so a hosted project's sign-in lasts as long, and a device signed out of Crew stays signed in to a hosted project until its token runs out (M19 decides otherwise if it must). `sessions.days`, 1 to 30, shortens the 30 days: a sign-in older than it is refused on every request with 401 `SESSION_OVER`, and the page offers the sign-in. A request without the time, which only an ingress without it during an update and `crew admin` send, passes and is not fresh. |
| A fresh sign-in, as built | Since 0.66 (M17): at most `sessions.fresh_minutes` old, 1 to 15. The ingress sends you to Google's sign-in again with `prompt=select_account`, the strongest prompt the pinned plugin passes: Google asks which account, and may skip the password. Every route of the API is in one of two lists of the server, the fresh ones and the plain ones, and a test fails for a route in neither or both; a fresh route that is not fresh answers 401 `FRESH_SIGN_IN`. A change of the machine's settings, by the PUT or Put back, is refused the same way, naming the keys, when it changes one of `updates.auto_install`, `install_after_hours`, `install_test`, `source_repo` and `publish`, `notifications.mail_to`, `network.mode`, `network.model_only_hosts`, `sandbox.sources`, `sessions.days`, `sessions.fresh_minutes`, `terminal.edit_mode`, `hosting.default_access`, and, since the security review of M17 phase 4, `notifications.mail_smtp` (the mail account's password goes there), `notifications.chat_webhook`, `updates.backup_copy_to` (a copy of every backup), `github.visibility`, and `improvements.approval`, and, since the security review of M17's Close (0.70), `agents.checks_use_another_family` (rule 15) and, until 0.79 retired it, `conversations.credentials` (the logins a conversation gets), and since the security review of M18 (0.71), `notifications.needs_you` and `notifications.news` (either turns mail off, and what comes meanwhile is not mailed later); and since 2.01, building a custom project sandbox image (`POST /api/projects/{p}/sandbox/build-image`) and `Allow` on a ticket waiting for `13.8` code-change confirmation (`POST /api/projects/{p}/tasks/{t}/code`, in the handler so `Refuse` still works without a fresh sign-in); a project's when its checks may run on the builder's family (`agents.checks_use_another_family` turned off; turning it on asks nothing), when its runs' or its checks' network mode, as it applies with the machine's, becomes or leaves LAN, or more people may reach its hosting (listed addresses, any Google account, everyone, or one more listed address), or, since 0.72, its hosted project may reach the internet again (`hosting.internet` turned on); a ticket's own network mode when the mode its runs take becomes or leaves LAN. The list goes beyond the row above where a key widens what a sandbox reaches or weakens the guard itself. Crew's own changes of a setting, such as a model, are not held. Crew checks the time of the new token only: it cannot see whether Google asked anything, so a browser with a live Google session that reaches the sign-in gets a fresh one with a click or none. What keeps a script off Crew's own page is the row on what agents wrote below. The fresh routes: opening the project terminal and its edit mode, and a terminal's connection, a run's included; Setup's terminal; the GitHub App's key; a personal token made, changed or renewed; Install, Install now and a roll back, and letting a held release install; Resume of Pause all and Stop all, and of the boot hold; signing a device out; and since 0.70 taking a held main, the project terminal's or a remote's (rule 13), and a project's files written out whole; since 0.71 the mail account (18.4); and since 0.71 Agree on a ticket an agent created that may change files that instruct agents (13.8, rule 13), in the handler, as the route's Refuse only narrows and asks nothing; and since 0.72 a hosted project's settings and secrets (19.3). Give the OK stays plain: it starts the work of a plan the operator made, and Pause stops it. The page: a refusal opens one dialog with Sign in again, which goes to the ingress and back to the same page, and Not now for a fresh sign-in, which only the change waits for; a sign-in that is over and a device signed out have no Not now. The keys above stay editable on both settings screens and say that they ask for a fresh sign-in, and how many minutes this one has left; a terminal asks before it connects, as its connection cannot say why it was refused. |
| A fresh sign-in, at most 15 minutes old | Is asked for by what could hand over the machine or the credentials: opening a terminal and its edit mode, reading or changing a secret, creating or changing a personal token, changing how releases install, changing the mail address, LAN mode, making a hosted project public, Install and Install now, lifting a hold, and a roll back. The ingress sends you through Google's sign-in again and Crew checks the time of it. The next row says what is held as built since 0.66, which goes further: a ticket's own LAN, any widening of a hosted project's access, and more of the machine's keys; since 0.73 also turning a hosted project's internet on, its settings and secrets, and its roll back. |
| Requests | Every request that changes something, and every terminal connection, must come from a page of Crew's own address. The session cookie belongs to Crew's host name only, is not sent with requests from other sites, and cannot be read by scripts. As built: the ingress's portal writes it for the base domain, since the sign-in is at `auth.<base>`, so the browser sends it to every host under it; the ingress takes the portal's cookies out of every request it passes on, after its authorizer read them, so no app and not Crew's server gets them (since 0.66). |
| What agents wrote | Is shown as text. Markdown is shown without raw HTML, and attached files are served from an address of their own, so a file an agent wrote cannot act as Crew's page. |
| Two doors | The server listens in two places: one for the ingress, which is the only place the sign-in header counts, and one on the sandbox networks, which serves only the MCP, git, the broker, the proxy of Model only and Sources (13.6, since 0.43), and Sources' module proxy (since 0.61). The ingress's door answers only a request from the ingress's network or the loopback, which closes it to every sandbox and hosted project whether the server knows it yet or not (since 0.86; 13.6 says how the server learns that network), and finds nothing either for a request that arrives at the server's address on a sandbox's bridge, or that comes from any address on a sandbox's or a hosted project's bridge, at any address of the server, once it knows that sandbox (since 0.85). Root on the machine is not a third door: `crew admin` is run through Docker on the machine, never over a network (16.11). |
| Devices | Settings lists every signed-in device. Any of them can be signed out there. How it is built (since 0.66, M17): a device is one Google sign-in, by the token's id, which is the portal's session id. It lasts while the browser runs, so a fresh sign-in in the same browser keeps it; after the browser was restarted the sign-in has a new one, and Crew hands it to the device: before the page goes to the sign-in it asks for a nonce, good once for 10 minutes, and comes back with it, so the device keeps when it was first seen. A nonce used or run out, another email, or a device signed out takes nothing over, and the sign-in is a device of its own. A device is written at its first request and its last time at most once a minute; check mode writes none. Signed out, every id it has is refused for good with 401 `SIGNED_OUT`, and Sign in again goes through the ingress's logout, which removes the session id, and so makes a new device. A device goes 31 days after its newest sign-in, when no token of it is taken any more; one signed out is kept for good, as a browser that still holds its session id would sign in with it again (schema step 72). |

### 20.4 Visual Software Factory control plane (M24 to M25, since 1.47)

In front of the `Agent API` (`11.10`) and the rest of the 7-module stack (`5.1`), Crew's containerized `shadcn/ui` web application evolves into a visual Software Factory control plane (`Direction A` inset sidebar shell locked in `docs/plan/simulation/ui-sim/DECISION.md`, **shipping all `40` runtime-switchable themes** — `11` Product &amp; AI-Native, `9` official `shadcn/ui` presets, `20` Dotfile &amp; Editor classics — with light/dark mode toggle and live **Theme Swatch Gallery** picker `Themes (40)` persisted per operator; prototyped in `docs/plan/simulation/ui-sim/index.html` and `docs/plan/simulation/crew-simulation.html`, `R214` to `R221`):

- **Ten core operational surfaces per factory:** Groups each project factory around `Factory Line` (live pipeline visualization from Specs -> `Tasks API` -> `@coordinator` -> `@builder` -> parallel `[Review | Security | Test]` -> `main`, plus the `max_tries` -> `@researcher` branch), `Board` (Linear-speed keyboard Kanban with YAML ticket metadata), `Task Detail` (full YAML frontmatter, ACP stream, `tries / max_tries`, checks, and linked `#<project>` feature thread), `Specs & WORKFLOW.md` (two-tier foundational and feature specs outside code `Backlog`, showing both `@user`-initiated planning and autonomous `@agent -> @planner` feature decisions plus repo workflow contract), `Chat Rooms` (lightweight Slack-like `#<project>` channel per factory + one `feat/<NNN>-<slug>` thread per feature with `@security` routing, orthogonal `kind`/`intent` & `chat_message_addressees` delivery pills, `"Posted to room; nobody woken."` no-op feedback, `@user`-only `Interrupt active turn now` `steer` toggle, `bodyRunes > 4000` offload indicators, 1-click keyed Choice Prompt cards showing `v<n>` / `Superseded` / `direct` vs `agent_interpreted` provenance, and `visualViewport` keyboard resize + `touch-action: pan-y pinch-zoom` mobile layout), `Knowledge API` (cross-project bug/issue advisories and reusable architectural patterns), `Skills Registry` (`12.11`, searchable 4-tier catalog across Base, Cross-Factory Shared, Dream-Synthesized, and Vendored `VENDORED.md` skills with static AST scan verdicts, `SKILL.md` inspector, and live warm-VM sync), `Memory API` (project `Dreamstore` `0.00` to `1.00` validity bars + scoped Dreaming proposals), `Agent API` (live `agy acp --stdio --process-per-session` peer sessions, health, slots, and turn/steer controls), and `Runtimes & Storage` (`ComputeRuntime` Kata pause/resume/snapshot controls + `PostgreSQL | SQLite` State DB and `Local FS | GCS` BlobStore health).
- **Live workflow visibility:** Renders active `agy acp --stdio --process-per-session` peer sessions, `Tasks API` budget/trajectory bindings, bounded agent-to-agent chat hops (`hop N/3`), `tries / max_tries` indicators, clean-context research briefs, and Dreamstore validity bars (`0.00` to `1.00`) in real time.
