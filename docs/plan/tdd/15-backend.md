## 15. Backend

### 15.1 Code layout

Crew's source is an Apache-2.0 repository (`CREW_SOURCE_REPO`, e.g. `your-org/crew`), with two Go modules: the server, `github.com/kesokaj/crew`, and the ingress, `github.com/kesokaj/crew/ingress`, which is built into Caddy (17.1). While the source repository is public under `LICENSE`, runtime images and release registries remain operator-managed (16.12). The settings, the drafts, and the improvements are not in it: they are in the database (10.3). The packages marked "adapted from styrman-crew" came in as files (`THIRD_PARTY.md`, 17.1). Everything else is written for Crew.

Every test and every milestone that says "fixture repository" or "fixture project" means it. Where a test needs GitHub, it uses a private repository that a test setting names, never one named in the code.

The server keeps few dependencies. One of them is a PostgreSQL driver.

### 15.2 Orchestrator

A reconcile loop runs on every board change and on a timer. One orchestrator serves every project. A subagent run starts when its stage has room and the machine has room. A lead run is placed in the global queue and starts when a lead slot of its CLI is free and the machine has room. Every run the orchestrator starts belongs to a subtask, which it creates first (7.11).

| State | Action |
| --- | --- |
| Plan draft with a message from the operator | Queue the planning agent (class `operator_waiting`) |
| Project created, no breakdown | Queue the lead to break the plan down |
| Breakdown sent back with a comment | Queue the lead to revise it |
| Project waiting for its OK | Start nothing. Its tasks are in Planning, and it is in the inbox. |
| Project OK given | Move every task in Planning to Backlog |
| Task in Backlog, Analysis under its limit, not on hold | Move it to Analysis and queue an analysis run (class `analysis`): the lead, or a reviewer for a task the lead created |
| Analysis gave notice of a new feature | Mark the task in Analysis as a new feature and start its 24 hours. It is in the inbox, with the time it goes ahead. |
| A ticket's checks failed on `main` after work came in from outside Crew | Create a fix ticket (7.12) |
| The operator sent a message in a conversation | Start its sandbox if it has none, set the model and the effort on the first turn, and run one turn in the way 12.10 allows |
| A conversation's sandbox had no message for `idle_minutes`, or one more is needed than `max_sandboxes` | Remove the sandbox and its home. The conversation, with the CLI's own files, is in the database. |
| A new feature's 24 hours have passed, and it is not on hold | Mark it ready |
| The operator pressed Approve now, Discard, or Hold on a new feature | Mark it ready, close it, or stop its clock |
| Task ready in Analysis, dependencies Done, In progress under its limit, not on hold | Create its branch, move it to In progress, and start a builder, or the first subtasks the lead planned |
| Task in In progress with queued subtasks | Start every one whose `after` is done and whose files no running subtask names, up to `max_parallel_subtasks`, each on its own `sub/` branch |
| A parallel subtask ended | Run its own check, merge its branch into the task's branch, and after the last one run the task's checks on the result. On a conflict or a failed check, start one builder subtask to join the work. |
| A task reached `max_fix_rounds`, or its run stopped twice | Queue a lead run to look at it again (class `analysis`). The first time the lead writes a new approach. The second time it cancels the task and creates the tickets that replace it. |
| The tickets agents added passed their share of the plan's tickets | Pause the project. Running runs finish. It is in the inbox. |
| Task passed a stage | Move it to the next stage that is on and that the task does not skip. If that stage is full, the task waits where it is. |
| Task in Review, Test, E2E, or Verification with no run, stage under its limit | Start that stage's agent |
| Task failed a stage, or the merge check | Leave it in its stage. Create a fix subtask and start a builder. When the fix is pushed, start the stage's agent again. |
| Task passed its last stage | Put it in the project's merge queue (7.10) |
| Task left In progress, and the project has a GitHub remote | Open the task's pull request, and keep it up to date with the records (7.12) |
| Skipped task whose condition is now met | Queue its analysis again. It stays in Analysis |
| Every approved task is Done, cancelled, skipped, or discarded, and nothing is waiting for analysis | Queue the lead for the final report and retrospective |
| Task ended | Start the summary writer for it |
| `main` changed | Index the documentation again, and mark pages whose covered code changed without them (9.9) |
| Watchdog stop | End the run and retry the subtask once. After a second stop, queue a lead run to look at the task again (7.7). |
| All lead slots of the run's CLI are taken | It waits in the queue, in class order and then by priority. Subagent runs are not affected. |
| No room on the machine | The run waits until a sandbox is removed |
| Unanswered operator comment | On the plan or the breakdown: start the lead for it. On a ticket with a run that is going: send it into that conversation. On a ticket with no run: keep it for the prompt of the next run on that ticket (11.6). |
| Project paused, or task on hold | Start nothing for it |
| Feedback to handle, memory over its cap, or documentation marked out of date | Queue a housekeeping run, if none is going and none started in the last 24 hours |
| The improver is due: its schedule, or enough finished tasks since its last run | Queue an improver run (class `improvement`) |
| An improvement is proposed | Run the generic check, then queue eval runs in each project that has cases |
| An improvement passed its evals | Create a ticket for it on Crew's own board, already approved, so it ships like any other change (16.2). Runs that start after that release is installed use it. |
| Enough tasks have finished on a release that holds an improvement | Measure the effect and write it into the improvement. If it is worse, take the improvement out again (10.5) and send news. The inbox gets an item only if the roll back fails. |
| A CLI reports a subscription limit | Mark the group of that run's model as limited until the reset time. A run for that group starts on a model of its bracket in another group that can run when the rule for checks allows it, and otherwise waits (12.7). |
| A run of the builder, the reviewer, the tester, the E2E tester, or the verifier ends | Count it for the entry it ran on. Then apply the rules of 12.3 for that agent: end a comparison that has its runs, go back when the watched runs are worse, keep a change when they are not, and change to another entry when the rules and the brakes allow it. Each of these writes a row in `model_choices` and a line of news. Nothing here starts or stops a run. |
| The list of models is a day old, a sign-in succeeded, or the version of a CLI changed | Read that CLI's models in a login-check sandbox and update the `models` table (12.3) |
| A login check fails twice in a row | Mark that CLI as signed out. Stop its runs and keep the conversations. A stopped run continues on its agent's next choice on another CLI when the rule for checks allows it, and otherwise waits. Put one item in the inbox, and send its mail at once. |
| The operator has signed in again and the check passes | Continue the stopped runs in new microVMs, and start the waiting ones. |
| An update or a roll back has started | Start no new run until the new version has passed its check. Running sandboxes continue (16.7). |
| A run ended, however it ended | Fetch its branch, write the run record and the subtask's result, save the CLI's own files, close the trajectory, and remove its microVM and its home |

### 15.3 The database

Crew's database is PostgreSQL, in its own container on the machine (R188). It is the one store of everything Crew saves (6.5), and the server reads everything it knows from it.

| | |
| --- | --- |
| Container | `crew-db`, one of the core services in Docker Compose, with the official PostgreSQL image at a fixed version. It is part of the Crew release (16.1). |
| Data | One directory on the host's SSD, `/var/lib/crew/db` (`<CREW_DATA_DIR>/db`), mounted into the container |
| Who can reach it | The server and the updater, over the core services' own Docker network. It has no port on the machine's address. No sandbox has a route to it, and the start-up check of the firewall tests that too (16.10). |
| Roles | `crew` for the server. `crew_migrate` for the updater, which may change the schema. `crew_read`, which can only read. The passwords are files in `/etc/crew/secrets/`, made once at install and given to the containers as Docker secrets (16.11). |
| Memory | 2 GB of the machine's reserve (13.10) |
| When it is down | The server shows a page that says so and starts no run. Running sandboxes keep working and keep writing to their spools (12.4). Docker starts the container again. |

**What the server uses it for.**

| Use | How |
| --- | --- |
| Records | Tickets, subtasks, and every record are rows. A change is a transaction with its row in `changes` (6.4). |
| The queue | Pending work is rows in `jobs`. A job is taken with a row lock, so one run starts once, also after a restart. |
| The live view | The database tells the server when rows arrive, and the server passes them to the browser. |
| Search | PostgreSQL's own text search, over tickets, records, summaries, turns, and documentation |
| Trajectories | `events` is split by month. A month that has ended changes only when a project or a conversation is deleted, so it is backed up once, and again after such a delete (16.9). |
| Analytics | Queries over the same rows. The results are cached in `metrics`. |

**Secrets in the database.** The server encrypts a credential before it writes it, with a key in a file on the machine, `/etc/crew/secret.key`. The key is not in the database and not in a backup. So a copy of the database alone shows no login. On a new machine without that key file, the operator signs in again in Setup.

**Changing the schema.** The schema changes through numbered steps in Crew's source, `internal/db/migrations`. The updater applies them, first to a copy (16.4). PostgreSQL applies a step as one transaction, so a step that fails changes nothing.

**Looking inside.** `crew-ctl db shell` on the machine opens `psql` with the role that can only read. The Database screen in the app shows the size, the tables with their rows, and the last backup. Nothing else writes to the database: only the server, the updater during an update, and `crew admin` for `migrate` and `restore`, which only root on the machine can start.

**A new version of PostgreSQL.** Either kind is a release that changes code, so it waits for Install (16.3). A small step up needs nothing more. A new major version changes the files on disk, so the updater moves the data with a dump and a restore.

**The core tables.** These are the columns behaviour depends on. The rest is detail for the schema.

**The first schema** (M1) holds only what M1 to M3 use: the settings, the credentials, `changes`, `jobs`, the sandboxes, `subtasks`, `runs` with their prompts and `run_tokens`, the conversations with their turns, `events`, the CLI's own files, and the models. Each later milestone adds its tables as numbered changes. The rule of two releases (16.6) starts with the first published release. Before that a schema change may be made in one step.
