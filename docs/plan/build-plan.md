# Build plan

> A copy of section 23 of `agent-kanban-tdd.md`, version 2.01. The design is the source: change it there, and run `python3 tools/plan-copies.py`.

**What you need before the build starts.** The builder cannot get these by itself.

| What | For |
| --- | --- |
| Your own user on the host machine, with sudo. A coding agent that is installed and signed in under it, on the machine itself and not in a legacy `styrman-crew` sandbox. It works under your user, and uses `sudo` for single commands that need root without putting any account into the `docker` group. | Every milestone until Crew builds Crew (M16) |
| git under that user, with your name and mail, and access to GitHub (`CREW_SOURCE_REPO`, e.g. `your-org/crew`) | M0 |
| Paid extra use switched off in your CLI account | M0, before a test that reaches a limit |
| You at a browser, for the sign-ins in Setup | M0, M2 |
| Historical provenance commits (`styrman-crew` at `5c9e6fb`, `styrman-harness` at `43faca0`, `THIRD_PARTY.md`) | The parts initially adapted (section 17) |
| An open-source Apache-2.0 source repository on GitHub (or local remote) | M0 |
| The address Crew gets, with `auth.` before it, both pointing at the host machine (or a DNS token that lets the ingress write them) | M1 |
| A Google sign-in client with the redirect address that `.env.example` gives | M1 |
| A second registered domain, only if you want hosting | M19 |
| What you still want from styrman-crew's projects, copied out | Before step 3 of 17.6, which M1 starts with |

Each milestone ends with something that can be demonstrated. The order changed in 0.20: an agent's record and move tools come with the first autonomous ticket, the limits and recovery paths come before Crew runs unattended, and the inbox is not needed before the web UI.

| # | Milestone | Done when |
| --- | --- | --- |
| M0 | Spike | The repository was bootstrapped with these documents in `docs/plan/`, `spike/`, and `testdata/agy/` (later open-sourced under Apache-2.0 at design 2.01). The questions of section 24 that are marked M0 are answered on the reference host with styrman-crew before it is removed, and this document is updated. The spike also delivers what the tests replay: recorded outputs of `agy` for a normal run, each quirk in 12.2, a model of each family, `agy models`, and `/usage`. A test that runs a subscription to its limit needs your yes. Without it, that recording is made the first time a real limit is met, and M0 is done without it. Every recording goes through the scrub script before it is committed (16.12). `versions.lock` gets its first values from the runtime pins. |
| M1 | Crew's repository, database, and machine | The host setup has installed Docker, Kata, and Cloud Hypervisor. `crew-db` runs in its own container, with its roles, its first schema (15.3), and a plain dump every day, made by a job in the server's container. The source repository holds the skeleton of Crew's own server and UI, `crew-ctl`, and the parts copied from styrman-crew, renamed: the sandbox orchestrator, the host setup, the firewall, the runtime image, the credential store and broker, the setup microVM, the terminal bridge, and the ingress with its sign-in. Each copied part comes with the packages it imports and passes the tests that came with it (17.2). The ingress has one fixed route to the server and no Docker socket. `harness/` holds the adapted harness. Any prior styrman-crew installation on the host is removed first, with its own uninstall (17.6). The runtime image has `agy` and the harness built in, without `sh-agent`. `crew-ctl doctor`, `install --build`, `status`, `edit`, `logs`, `backup`, and `uninstall` work on a fresh machine from one file of answers, and install does what the table in 16.11 gives for M1. `crew-ctl migrate` applies a schema change, `crew-ctl settings export` and `import` work, and a newer checkout is installed over the running one. `versions.lock` holds every version, and `make check` runs the tests and the first checks for a clean repository (16.12). |
| M2 | Setup and credentials | Setup is the first screen, before any project. The operator sets up the git identity, an SSH key, `gh`, the GitHub App, gcloud, and `agy`, and the broker gives each sandbox what it may have, with a temporary GitHub token that can only read, shown on a fixture repository. A sandbox gets the login of one CLI only. A login file for another account is refused. `crew-run login-check` and `crew-run creds` are built here, and the login check runs on a schedule. From M3 it also runs before each run. Setup and the Agent CLIs screen are the first two screens of the web UI. A login that is taken away is noticed and shown there. That signing in again makes stopped runs continue is shown in M3. The inbox item comes with M7. |
| M3 | One headless run | `crew-run turn` starts `agy` headless in a run microVM, through its adapter, on the fixture project, with the files of 12.4. The git endpoint exists in its smallest form: one repository, a run token, and the branch that keeps work in progress. The run has a subtask row with no ticket. The backend reads the events from the spool in the run's home and writes them to the database. The monitor shows the run's state, and the watchdog stops a silent run. The run can be stopped, with its work in progress kept, and continued in each way of 12.10. The third way is shown with the last turns only, until summaries exist (M6). A run that stopped for a sign-in continues after it. The stop reasons of 12.4 are recorded, and `FakeHarness` can play them. Nothing outside the adapter names a CLI. Every turn, every event, and the CLI's own files are in the database, and a run whose events cannot be written is stopped. The prompt is saved. As many runs in parallel as the spike found the plan carries, ten if it can, stay signed in. Install's proof now includes a stored event (16.11). |
| M4 | Board core | A project has its rows in the database and its code in a repository. Tickets with a number, a why, a what, a goal, and checks move through the fixed and the optional stages by API, with the project OK, analysis decisions, limits, and WIP limits. Every change is one transaction with its row in `changes`. A project can be exported and imported. No agents yet. |
| M5 | Plan to OK | The first tools of the Crew MCP exist: the ones the planning agent and the lead need for a plan and a breakdown, with a token for a plan that has no project yet. The baseline holds its first prompts, for the planning agent and the lead, and the descriptions of those tools. The operator develops a plan with the planning agent, creates a project with a repository on GitHub, the plan is added, the lead breaks it down into tickets in Planning, and the operator gives the OK. |
| M6 | One autonomous ticket | A ticket goes from Backlog to Done with no operator: analysis, build, review, and test, each as a run in its own microVM (since 1.37, as an isolated git worktree and `agy acp --stdio --process-per-session` session inside the project's warm microVM `crew-proj-<project>`), the goal loop, the checks on top of `main`, and the merge. The core of the Crew MCP is there: the tools that ask, record, and request a move, and `decide`. Checks are read from the database, and the checks that decide run in a check sandbox. The baseline holds the prompts of the builder, the reviewer, and the tester. The ticket's summary is written by a run of the judge kind. A comment on a ticket reaches the run that is going, or waits for the next run on that ticket. Only a comment on the plan starts the lead (11.6). |
| M7 | Web UI | The board, the task view with the running agents, their model and effort, the prompt, the source plan, and the subtasks, the activity feed, the inbox, the Decisions list, and the Trajectories and Database screens. The Git screen and the git part of a ticket. The project terminal with its edit mode, and the jump into the sandbox of a running run. The Plans screen, where the prompt writer proposes a better wording of the operator's first message, with Use the rewrite, Edit, Send mine, and Rewrite again. The menu on selected text, with Improve text and Review text, in every place the operator writes. Every rewrite is saved with the choice, and the signal is recorded (7.2). |
| M8 | Models, lead slots, and the quota guard | Crew reads the models of each CLI, and the Models screen shows every one of them and gives them to agents. At a limit or a lost sign-in a run moves to its next choice, or waits. Every run records its model and effort and where they came from. A project or a ticket can pin another model or effort. A check runs on another family than the build. Results are measured per role, CLI, model, and effort. Lead slots are counted for each CLI. The lead queue goes by class and then by the ticket's priority. Crew chooses the entry and the effort for the builder from those results, by the plain rules of 12.3: it tries other entries with one run in ten, changes by itself, tells the operator in the app, and goes back if the change was worse. The operator can set an agent by hand, and that wins. A comparison can be started. The agents that check are chosen the same way once bugs are recorded (M12), and the E2E tester and the verifier once they exist (M10). Install fills `agents.roles` from the baseline. The quota guard holds runs back at the limit of their group of models and shares a window between projects. |
| M9 | Crew MCP: tickets and subtasks | Agents create tickets, which Analysis approves, skips, discards, or gives notice of as a new feature. A new feature goes ahead after 24 hours, shown in the app, with Approve now, Discard, and Hold. Agents create subtasks on their own ticket. Subtasks that do not depend on each other run in parallel on their own branches and are joined by the backend. The Crew MCP screen shows the tools and every call. The operator's own tools can use the MCP with a personal token. |
| M10 | Network modes, optional stages, pull requests | Model only mode works for each CLI. E2E and Verification can be switched on per project, and a project can add a stage of its own. `judge:` checks run. With a GitHub remote, each ticket has a pull request, Crew fetches what changed there, and work that came in from outside is checked. |
| M11 | Limits, and tickets that cannot get through | Since 0.53 no limit is in dollars and no cost is estimated: a run records its tokens (7.7, 12.7). A ticket never moves to an earlier stage: a failed stage is fixed in place. A ticket at its fix-round limit, or with two stopped runs, goes to the lead: one new approach, then cancelled and replaced by other tickets. A project pauses at its limits. Pause all and Stop all work. The disk guard works. The final report runs. Revert, an amendment to the plan, archive, and delete work. The recovery paths of section 21 are tested where their parts are built; each later milestone tests the rows of the parts it builds (since 0.45). Crew may run unattended once the daily backup (M14) and the mail (M18) are also in place. |
| M12 | Documentation, memory, bugs, feedback, skills | A project's own skills and context on `main` reach every run, and `request_skill` creates a skill ticket. The pages in `docs/` are indexed and shown. Tickets update their pages. Memory reaches every run through the Crew MCP. Bugs become fix tickets. Agents give feedback. Housekeeping runs (since 0.44, from M11). End-to-end tests that pass or fail at random are run once more in a new sandbox, and a result that keeps changing becomes a bug (21; since 0.45, from M11). The agents that check join Crew's choice of a model, by the defects that escaped them (12.3; since 0.46). |
| M13 | A whole project, and many projects | A project runs from its OK to Done with nobody acting, as a test on fixture projects. The lead slots, the capacity check, and the quota guard hold across several projects. These recovery paths of section 21 are built and tested (since 0.45, from M11): a project's setup that fails, an end-to-end run that cannot start the application twice in a row, a pull request merged or changed on GitHub by someone else, a builder who weakens their own test, and the analysing agent that approves too much, with `approvals.created_task`. |
| M14 | Versions in the app | A release is built once into a folder of images. The updater loads it, checks it beside the running version, switches, and watches. The Versions screen shows every release and the updater's steps. A release that passed the gate, which at this point is the tests on the built images, is tagged and published on GitHub with notes and images, the notice is shown in the app. A release that changes only prompts and harness text installs after 24 hours unless it is held, and every other release waits for Install. `crew-ctl update` and `rollback` use the same updater, over its socket. The install test on a fresh virtual machine is part of the gate where it is set up. A release that fails its check changes nothing, and a version that turns unhealthy is switched back. `crew-ctl` can build, install, roll back, and restore. The daily backup becomes the tar.gz file with the month files (16.9), in place of the plain dump of M1. Every new microVM uses the new image. |
| M15 | Analytics, evals, and the Crew level | Signals from all projects, eval cases, the improver, and the meaning of "not worse". A project's overrides are applied and measured. An improvement that passed its evals becomes a ticket. From M16 it ships in a release, its effect is measured, and a worse result is taken out again by Crew. What followed a rewrite of a prompt is measured, and the improver reads your edits of rewrites (7.2). The retrospective runs (9.8; since 0.46, from M12). |
| M16 | Crew builds Crew | Crew's source repository is a project on its own board. The daily look for new CLI versions creates tickets there. A release candidate is built once, gated on the built images with one real ticket and the eval suites, announced, and installed by the updater: by itself after 24 hours when it changes only text, and on Install otherwise. Improvements ship this way. |
| M17 | Settings in the UI, sessions, and the last hardening | Both sets of settings can be edited from the UI. Sessions ask for a fresh sign-in where 20.3 says. Kata is moved to its current line behind the integration tests, unless M1 already did. Looking after the machine works as in 16.10: security updates, certificates, and the restart. Retention is tested. A second machine is installed from a release with `--registry-token-file`, and gets a later release the same way (16.12). Two microVMs in a row that do not start hold new runs and put the Kata and KVM check in the inbox, and the inbox says when the database can be written again (21). |
| M18 | Notifications | What needs you arrives as a mail, where a link chooses and Confirm decides. News arrives as one mail a day. This can be built any time after M7. Web push for the phone comes later and is not a milestone yet. |
| M19 | Hosting | Host locally builds a project's image, starts it as a sandbox, checks it, and gives it an address through the ingress that can be reached from the internet, private by default, with the sign-in of the ingress. Deploy again, follow `main`, roll back with the data copy, stop, settings and secrets, and logs. A project with no Dockerfile gets a ticket for it. |
| M20 | Conversations | The operator starts a conversation about a project or about none. The agent answers and works in an ephemeral sandbox. Every turn is saved. The sandbox is removed when idle and the conversation goes on with the next message. Make a ticket of this, and Start a plan from this. Every ticket has a chat with the assistant, for a running ticket and for a done one, with Tell the agent, Make a ticket of this, and Remember this. Marked text in the task view becomes a comment in the chat (11.9). This can be built any time after M8, which has the lead slots it uses. Remember this needs the memory of M12. |
| M21 | Agent API, Harness Runtime, ComputeRuntime, `WORKFLOW.md`, and YAML tickets | Exposes the `Agent API` over `Harness Runtime` (`agy acp --stdio --process-per-session`, `1 session = 1 peer agent`, internal CLI subagents disabled, keeping `internal/cli/` open for future `pi` and `claude` adapters) and formalizes Crew's existing Docker + Kata suspend/resume & snapshot primitives behind `ComputeRuntime` (`13.12`) with a future Kubernetes seam. Copies `baseline/WORKFLOW.md` into each new factory repo root, reads it from `main` under `13.8`, and syncs `.crew/tickets/<KEY>.md` YAML frontmatter with `StateDB`. |
| M22 | Tasks API gate, Coordinator, and stop-and-research loop | Enforces zero untracked agent work through `Tasks API` (`R217`): executable code tickets enter `Backlog` ranked per factory by `@coordinator` and scheduled machine-wide by the Global Queue, while non-code `spec`, `research`, `dream`, and chat-spawned tasks remain tracked off-board. Adds the `max_tries` circuit breaker that stops stuck runs, snapshots WIP, and dispatches `@researcher` in a fresh ACP session with a clean diagnostic prompt. |
| M23 | Two-tier Planning Studio (manual foundation + autonomous peer-to-`@planner` feature specs) | Separates **Project Planning** (`.crew/specs/000-foundation.md` + initial `WORKFLOW.md`, gated by `@user` Project OK) and **Feature Planning** (`.crew/specs/NNN-<slug>.md` outside `Backlog`), enabling both `@user`-driven planning and autonomous peer-agent -> `@planner` question/decision loops inside feature threads (recording `decisions/` and emitting YAML tickets into `Backlog`, escalating to `@user` only on `000-foundation.md` scope changes, `13.8` protected files, or `approvals.feature_specs: manual`). |
| M24 | Lightweight internal Slack-like chat (`#<project>` channel + per-feature threads) | Replaces standalone 1:1 `Conversations` and single-assistant `Ticket chat` with one canonical `#<project>` channel per factory and one thread per feature (`feat/<NNN>-<slug>`) inside the containerized web app, where peer agents and `@user` share messages (`post_chat` / `read_chat` / `ask_planner` MCP tools) bounded by `max_agent_hops` and `internal/fence`, and minting trackable `Tasks API` items for actionable requests. |
| M25 | Visual workflow control plane (all `40` themes shipping), Skills Registry UI, Trajectory Store, and split storage (`BlobStore` + `SQLite` mode) | Upgrades the web control plane (`ui-sim` `DECISION.md` locked to `Direction A` + **all `40` runtime-switchable themes** with light/dark toggle and `Themes (40)` Swatch Gallery) over the 7 modules with a live visual Factory Line graph, Linear-speed keyboard Kanban with YAML ticket inspection, the 4-tier `Skills Registry` catalog & `VENDORED.md` inspector (`12.11`), `#<project>` + feature-thread chat UI, full-text/facet search over the Trajectory Store, immutable `BlobStore` (`Local FS` or `GCS`) offload for trajectory archives and sealed snapshots, and optional embedded `SQLite` WAL `StateDB` mode (`R220`, `R221`). |
| M26 | Memory API (Dreamstore & scoped Dreaming), Skills Registry backend, and cross-project Knowledge API | Evolves project memory into typed `Memory API` Dreamstore (`episodic`, `semantic`, `procedural`) with automated path-drift decay, pass boosts, and `< 0.4` quarantine scoring; scopes Dreaming strictly to harness context micro-adjustments, new `SKILL.md` synthesis, and SHA-pinned external skill downloads behind `@user` approval; and delivers the `Skills Registry` (`skills_registry`/`skill_installs`, static AST vetting, live warm-VM sync, `12.11`, `R221`) alongside the installation-wide, secret-scrubbed **Knowledge API** (`9.11`, `R218`). |

**Accepted as not shown (since 1.17).** Two parts of a "done when" were never shown, and the operator accepted both as not shown (session 84). M18's mail was shown against a stand-in mail server only: the real send through Google's SMTP needs the operator's mail account in Setup and Send a test message, which the operator dropped in session 37, so no mail account is stored. M19's address that can be reached from the internet needs a real apps domain with its DNS record and its certificate, which are the operator's (section 24, item 23), and hosting was shown without one. Either is shown when the operator stores a mail account or sets up the domain. Nothing else waits for them.

The rules of 0.27 for safety are not milestones of their own. Each is built with the part it guards: the token per project and the test of a login in M2, the stop reasons and work in progress in M3, the check sandbox in M6, requests from Crew's own pages in M7, reading the limits in M8, and `may_change` with what waits for you in M9.

Prompts, trajectories, and run records are complete from M3, and signals from M6. So summaries, analytics, evals, and the Crew level can use the whole history.
