How Crew works

Crew is a kanban board that is worked by AI agents instead of people. You write a plan with an agent, create a project, and give one OK. Agents then take every ticket through every stage, each run in a sandbox of its own, and Crew tells you when something needs you.

This page goes through all of it: the parts and how they talk, how a project runs from plan to hosted, what happens to one ticket, and every screen of the app. It describes the design. Nothing here is built yet, and the screens are from the simulation.

Historical snapshot (design 0.32): This walkthrough illustrates the initial design simulation before Crew moved to agy-only runs (0.42), removed gcloud from run sandboxes (0.79), introduced warm project microVMs (1.37), and published its source under Apache-2.0 (2.01). See docs/install-and-uninstall.md and docs/plan/agent-kanban-tdd.md for current v2.01 behavior.

The parts

The whole system

Everything runs on one dedicated Debian or Ubuntu machine (originally benchmarked on 24 cores, 64 GB, and a 1 TB SSD; any prior styrman-crew installation is removed first). You reach it from outside. Agents never run on the server itself: every run gets a small virtual machine of its own, and about 16 fit at once.

  • You open Crew in a browser, signed in with your Google account. Your own tools, such as agy or claude on your laptop, can use the same server with a personal token.
  • The Crew server writes main and the database. Agents never do: they ask, and the server decides. You can push to main yourself, from the project terminal in edit mode.
  • A sandbox is a microVM with its own kernel, files, and network. It exists for one purpose, most often one agent run, and is removed afterwards.
  • A sandbox reaches Crew in two ways: the Crew MCP, and git for its own branch. Crew keeps the credentials you set up in Setup, and copies into each sandbox what it may have: the login of the CLI it runs, the git identity, and a GitHub token that can only read (gcloud was removed from run sandboxes in design 0.79).
  • GitHub. Crew reaches it over SSH with one key, and with gh for what a key cannot do: creating a repository, pull requests, and release pages. Both stay with the server. A sandbox gets a token that can only read and stops working after one hour, so nothing in a sandbox can push.
  • The machine is set up once by one script, copied from styrman-crew: Docker at a fixed version, Kata with Cloud Hypervisor as the runtime for microVMs, Docker's settings for it, and a check that a microVM starts. It is the same on Debian and Ubuntu.
  • The agents are command-line agents, run headless on your subscriptions: agy, the Antigravity CLI, and claude, Claude Code. There is no model API. Each CLI is behind one adapter, so another one, such as codex or opencode, can be added later. Crew keeps the models of both CLIs, and all of them can be browsed in the Models screen. Each role is an agent of its own, and its CLI, model, and effort are settings: a default that comes with Crew, your own choice for the machine or for a project, or a pin on one ticket. Crew acts as you: the agents work with your own logins.
  • The database is the brain. Tickets, records, settings, conversations, and trajectories are rows in it. Code and documentation are in git, on main.
  • Crew's own source is a project like any other. Agents work on it. The settings, the plan drafts, and the evidence of this installation are in the database, which no sandbox can reach.
The brain

Where everything is saved

The database is the brain of Crew. Everything Crew saves is in it, and it runs in its own container on the host. Git holds the code.

  • If Crew saves it, it is a row. Plans, tickets, records, settings, every conversation, and every trajectory are in the database. Nothing that must survive is only in a file or only in the server's memory.
  • The server keeps no state of its own. After a restart it reads the database, finds the running sandboxes, and goes on.
  • It is its own container, crew-db, with PostgreSQL. Only the server and the updater can reach it.
  • Agents never reach it. No sandbox has a route to the database. An agent asks the Crew MCP, which answers only for its own project.
  • Every change is kept. A change to a ticket, a record, or a setting adds a row to the history: who, when, and the value before and after. Rows are only added.
  • Git holds what is source: the code, the documentation, and a project's own skills. There is no board branch any more. A commit names its ticket, and a ticket names its commits.
  • A few things are files: Docker images, the data of hosted projects, the backups, and the one key that encrypts the credentials in the database.
  • Moving a project: the code is the repository. The rest can be written out as a folder of files and read back on another machine.
  • You can look inside on the Database screen, and on the host with crew-ctl db shell, which can only read.
From start to end

A project, from plan to hosted

You act at four points: the plan, creating the project, the OK, and hosting. Everything between the OK and Done runs without you.

  1. Plan. You say what you want. Crew first proposes a better wording of your prompt, and you choose which text is sent. A planning agent then asks about what is still open, and writes the plan with you. No project exists yet.
  2. Project. You create the project from the plan. Crew creates the git repository, on GitHub or on the machine, and stores the plan in it.
  3. Breakdown. The lead agent of the project reads the plan and the code, and splits the plan into tickets. Each has a why, a what, a goal, and a check. They wait in Planning.
  4. OK. You read the breakdown and give one OK. It fixes the scope and the budget.
  5. Pipeline. Agents pull tickets by themselves. There are 2 lead slots for each CLI to start with, and a lead run takes a slot of the CLI it runs on. When they are taken, it waits in a queue that goes by the priority of the tickets. Builders, reviewers, and testers are limited by the stage limits, by room on the machine, and by the limits of your subscriptions, which the projects share in turn.
  6. Done. When every ticket is Done, cancelled, skipped, or discarded, the lead writes the final report: what was built, what was skipped or cancelled, and what was learned. A ticket you add later opens the project again.
  7. Host. Press Host locally. Crew builds what is on main, checks it, and gives it an address.
  • Why. A planning agent works with what it is given. A prompt that says the goal, the reason, what is in and out, the limits, and how to see that it is done gives a better plan and fewer questions.
  • Where. In planning, the first message of a plan gets a proposal by itself. Everywhere you write, you select text with the mouse and choose Improve text or Review text. Review text changes nothing: it says what is unclear or missing. On the plan itself, both go to the planning agent, with the part you marked.
  • What the prompt writer may do. It keeps every fact, name, number, and limit you wrote. It adds nothing of its own except assumptions, which are marked and which you can strike. It asks at most three questions, and does not guess what would change the plan.
  • It never holds you up. Send mine is there from the first second. After 45 seconds, or when the call fails, your own text is sent as it is.
  • It is measured. Crew records which text you sent and what followed: the questions the planning agent asked, the breakdowns you sent back, and the tickets that passed the first time. What you edit in a rewrite improves the rules of the prompt writer.
  • Projects stay apart. The prompt writer sees earlier rewrites of the same project only.
The unit of work

A ticket, from idea to main

A ticket is the only kind of card. It has a number such as SF-42, a why, a what, a goal, and checks. Nothing is built without them. A ticket works as kanban: it only moves to the right.

  • Three ways in. From the breakdown, from an agent that saw something while working, or from you.
  • Analysis decides. The lead reads the ticket against the plan and the code as it is now, and approves it, skips it for now, discards it, or gives notice of it as a new feature. A skipped ticket and a new feature stay in Analysis. A ticket an agent created is never analysed by the agent that created it.
  • Every stage is another agent in a fresh sandbox. The builder never reviews or tests its own work.
  • A failed stage is fixed in place. The ticket stays where it is. The findings become a fix subtask for a builder, and the stage then checks again. A stage that is full of failing work takes no new work, which is the signal a kanban board is meant to give.
  • Only Analysis sets the checks. A builder cannot change them, and the reviewer is shown every test file a change touches.
  • Merging is one at a time. Crew merges the current main into the ticket branch, runs the checks again, and only then merges. A check that fails only sometimes is run once more and recorded as flaky. With GitHub and gh, each ticket is a pull request.
  • The summary is written by a separate step from the records, not by the agents that did the work.
  • Ask about it. Every ticket has a chat, while it runs and after it is Done. An assistant answers from the ticket's records, its trajectories, and its diff, and can try things in a sandbox of its own. It is not the agent that works on the ticket, so a question never stops or steers a run.
  • Mark text, and comment. Select text anywhere in the ticket and choose Comment. It goes to the chat with the marked text quoted, and the assistant says what it means and whether it is a problem.
  • From the chat to the work there are three buttons that only you press: Tell the agent, which makes a comment to the agent that works on the ticket, Make a ticket of this, and Remember this. A Done ticket is not opened again: a change is a new ticket.
  • A ticket never waits for you. One that passes its budget carries on, and the event is recorded. One that needed 3 fix rounds, or whose run stopped twice, goes to the lead again: one new approach with two more rounds. After that the lead cancels it and replaces it with other tickets, cut smaller. They are tagged to it and start in Backlog.
One level down

Inside a ticket: subtasks

The work inside a ticket is a list of subtasks. A subtask is one piece of work done by one agent run. Subtasks that do not depend on each other run at the same time.

  • Who creates them. The pipeline creates one each time the ticket enters a stage. The lead can split the build into several, and a builder can add one for more work inside its ticket.
  • In parallel. At most 3 run at once on one ticket, each on its own branch, sub/SF-42.2. Two that name the same files run one after the other. At most 6 are added per ticket.
  • Joining. Crew checks each subtask on its own branch, merges the branches into the ticket branch, and then runs the ticket's checks on the result. If they do not join, one more builder subtask joins them.
  • Every subtask keeps its prompt, its steps, its log, and its cost, so you can see what that agent was told and what it did.
The smallest piece

One run, in its sandbox

A run is one agent working on one subtask. It has full access inside its sandbox and almost none outside it.

  • The prompt is saved in its parts: the stage prompt, the agent definition, the ticket, the plan, the memory, and your comments.
  • The network switch has three settings per project: internet, model only, or your local network as well.
  • Which CLI and model. A model belongs to a CLI, so the model names the CLI. The model and the effort are the ones pinned on the ticket, or set for the role in the project, or the default, and the run records which. By default Claude models run through claude and Gemini models through agy. A reviewer and a verifier run on another family of models than the builder. When a CLI is signed out, or a group of its models is at its limit, a run moves to its agent's next choice that can run, on either CLI, or waits. A check never moves to the builder's family.
  • The list of models comes from each CLI: agy models prints it, and claude shows it in /model, which Crew asks the CLI for. Crew keeps no list of its own.
  • Crew chooses the CLI and the model, and you can override. For the builder, the reviewer, the tester, the E2E tester, and the verifier, Crew measures each model it ran on: how much passed the first time, the fix rounds, the cost, and the time. One run in ten tries another model of the agent's list. When another one has at least 20 runs, Crew changes to it by itself, at most once in 7 days, and tells you with the numbers: the builder to one that did better, or as well for less, and an agent that checks only to one that did as well for less, so that a model that passes everything is never picked. It watches the next 20 runs and goes back if they are worse. An agent you set yourself in Models is left alone, and Crew only shows what it would choose. A project's setting and a pin on a ticket always come first. No improvement and no release changes a model.
  • Credentials. Set up once, in Setup, outside the projects, and kept in the database, encrypted. A sandbox gets copies when it starts: the login of its CLI, the git identity, and a GitHub token (without gcloud since 0.79) that can only read this project's repository and lasts one hour. The SSH key and gh never enter a sandbox, so an agent cannot push to GitHub.
  • The login is the longest-lived one each CLI has: a one-year token for claude, and for agy its token file, which is used and stored every day. It is checked before every run and every 30 minutes. If a CLI is signed out, its runs move to the other CLI where they can. The rest stop and keep their conversations until you sign in again.
  • Limits. A run stops at 200 turns, after 60 minutes, or after 15 minutes of silence, and is retried once.
  • After the run the sandbox is removed, and its home with it. Nothing of a run is kept in files.
  • What is kept, all in the database. The trajectory, which is every message and tool call, every turn of the conversation, and the summary. All are kept for good. Each trajectory shows whether feedback was run on it and which eval cases were made from it.
Talking, and remembering

Conversations, and how agents remember

Not everything is a ticket. You can just talk to an agent, and it can try things in a sandbox of its own. And every run, with you or without, is stored so that the next turn knows what happened before.

  • A conversation with you is about one project, or about none. The agent works in an ephemeral sandbox: it starts with your message and is removed after 30 minutes without one. Your next message starts a new one, and the conversation goes on.
  • It can read its project, and do anything inside its sandbox: clone, run, test, write files. It cannot change main or the board. What should land becomes a ticket, which goes through the stages like any other, or a plan.
  • Every conversation is saved in Crew's database, turn by turn, until you delete it.
  • Every run is a conversation too. A headless run of a CLI runs once and ends, so Crew keeps the thread in its database: the id the CLI gave it, every turn, and the CLI's own files.
  • Continued in three ways. While the sandbox runs, the next message is one more line on the CLI's input. In a new sandbox, Crew puts the CLI's own files back from the database, and the CLI continues it: agy with --conversation, claude with --resume. When that is not possible, or the next turn runs on the other CLI, the conversation is rebuilt from the turns.
  • Who remembers. A builder that comes back for a fix continues its own conversation, so it knows what it built and why. A reviewer or a tester starts new every time, on purpose: a check must not remember its last verdict as its own.
  • Trajectories. Every run and every conversation has one: every message, tool call, and result, in order, written by Crew while it happens. It cannot be switched off. Each project has a Trajectories screen, and every run shows its own.
Agents adding work

How agents add work: the Crew MCP

Crew has its own MCP server. Every run is connected to it, with a token that names one project. It is how agents ask about their project, write their records, and create more tickets and subtasks.

  • Your own tools can read, create tickets, and comment with a personal token. A token can also be allowed to approve or discard a new feature, and to change a decision an agent recorded. That is off until you switch it on. A token runs out after 90 days.
  • Skills and context. The base comes from styrman-harness. It has one source, and the runtime image holds it in the form each CLI reads. A project keeps its own in its repository, under .agents/ and in AGENTS.md, and every sandbox of the project gets them when it starts. No image is rebuilt.
Your part

What needs you

Crew should need you as little as possible. Four things wait for you, and none of them is a single ticket. The rest tells you first and goes ahead, or just happens and is recorded.

Waits for you

  • The project OK It sets the scope and the budget.
  • A project limit that was reached The project's budget, or the share of work agents may add.
  • Signing in to a CLI again Only you have the subscriptions. Until you do, the other CLI takes the work it can.
  • A change to a hook, an MCP configuration, or a workflow These are code, so the ticket waits before it merges.
  • A release that changes code The server, the app, the updater, the runtime image, the scripts, or the stored format. You press Install.

Tells you, then goes ahead

  • A new feature an agent created After 24 hours. You can approve it now, discard it, or hold it.
  • A release of prompts and harness text Installs after 24 hours, unless you hold it. It changes no code.

Just happens

  • An open choice The agent decides and records it. You can change it afterwards.
  • A ticket that passes its budget It carries on, and the event is recorded.
  • A ticket that cannot get through The lead tries one new approach, then cancels it and replaces it with other tickets.
  • A stage that fails Fixed where the ticket stands. It never goes back.
  • Which model and effort a run uses The default for its role. You can set another for a project, or pin one on a ticket. A check moves to another family than the build by itself, and a run moves to its second choice at a limit.
  • A skill a project misses An agent asks, and a ticket adds it.
  • Tickets agents create that fit the plan Another agent analyses each one.
  • Every stage move, when its checks pass
  • Merging into main
  • An improvement whose evals are not worse
  • An override the lead proposes for its own project Applied when the project's evals are not worse.
  • Rolling back a version that is unhealthy or measured worse
  • Two presses answer it. A link or a notification alone never decides, because mail scanners open links.
  • Pause all and Stop all are two switches for the whole machine. While Crew is paused, no release installs and no new feature goes ahead.
  • Google Chat is switched off. It needs a Google Workspace account, which you do not have today.
Crew itself

Crew improves and updates itself

Crew sees every project, so Crew is also where the agents and the pipeline get better. What it learns reaches every project as a numbered release.

  • Signals go up, the baseline comes down. Nothing goes from one project to another. A proposal that carries a project's names or text is refused.
  • One version number covers the server, the runtime image, both CLIs, the harness, and the stored format. Rolling back changes them together.
  • The updater is a small container of its own. It starts the new version beside the old one and checks it before anything is replaced.
  • The last 5 versions are kept with their images, so rolling back rebuilds nothing. Every release is also a tag on GitHub (and with gh a release page), while built runtime images remain local or in your own private registry.
  • "Not worse" has a meaning. Each eval case runs several times before and after. A difference inside the spread between repeats is noise. A change that costs more than 20% more is refused.
  • Crew looks after the machine: the disk, security updates, the firewall, and the certificates. If no CLI works, you can build and install a release by hand with crew-ctl.
  • Backups stay on the host for now: one tar.gz file a day, with a dump of the database. Trajectories are kept for good, so the events of each month that has ended are dumped once into a file of their own, and a day's file holds the rest. The tag of every release is on GitHub. Nothing watches Crew from outside: if it is down, it is down.
  • A skill that several projects added is proposed for the base, and then ships to every project in the runtime image.
After Done

Hosting what was built

A built project can be hosted from the same machine with one button. It follows the same rule as Crew's own updates: build once, check, then switch.

  • Access works as in styrman-crew. The ingress asks for a Google sign-in and checks the address against a list. The project gets the signed-in address in a header and needs no sign-in of its own.
  • From the internet. The address can be reached from outside. Only your own Google address gets in until you choose otherwise: listed addresses, any Google account, or public.
  • Agents cannot deploy. You do, or the Follow main switch that you turned on.
  • The data is copied before every deploy, and a roll back can put the copy back.
  • Settings and secrets of a hosted project are entered in the app and kept in Crew's database, encrypted, never in git.
On a fresh machine

Install, update, and uninstall

Putting Crew on a machine, updating it, and taking it away again are features of Crew. One program does all three: crew-ctl. Everything runs in Docker, and Crew is built for nothing else. The source ships under Apache-2.0 with built runtime images kept private to your installation, and it installs the same way on every machine.

What it asks you for

  • The address of Crew The sign-in page is at auth. before it. For hosting, a second domain.
  • Your Google address The one account that may sign in.
  • A Google sign-in client Its id and its secret. You create it once in Google's console.
  • The repository of Crew's own code, if you want Otherwise Setup asks for it, and checks it with a push.
  • A DNS token, if you want Then Crew writes the DNS records and gets the certificates.

What it does by itself

  • Generates every secret The key file, the database passwords, and the session key. None is asked for.
  • Installs Docker and Kata At fixed versions, checked by checksum. What is already there is left alone.
  • Runs as a user of its own crew on the machine, and agent in every sandbox. Your account is in no path.
  • Records each step With whether Crew put the thing there or found it. Uninstall reads this.
  • Proves that it works A microVM starts, reaches Crew, and an event it prints is stored.

Private, reproducible, and clean

  • Every version is fixed One file names each version with its checksum. The same tag gives the same Crew on another machine.
  • No secret in the repository A checkout travels to every machine, so a secret in it would too. What differs between machines comes from the .env file.
  • Docker only Every part of Crew is a container. On the machine itself are only Docker with Kata, the firewall, the script crew-ctl with its files, and the data folder.
  • Another machine follows this one It gets the images of a finished release, never a checkout. Every release waits for Install there. It has its own sign-ins and shares no data.
  • Nothing is reported home Crew sends nothing about an installation to anyone.
  • Open-source source, reproducible local or private images. You put a checkout of the Apache-2.0 repository on the machine, and crew-ctl install --build builds Crew there. It needs no GitHub login. Another machine can pull finished runtime images from your own private registry, with a token that is used once.
  • The answers come first. Everything is asked for before anything is changed: in a .env file, or one question at a time when the installer starts. The logins are not asked here. They are set up in Setup, the first screen.
  • doctor checks the system, virtualization, room, the network, the names, and the answers, and it changes nothing. It knows a fresh machine from a repair and from an update.
  • Every verb can be tried. --dry-run prints each command it would run and runs none. A second install on a machine that has Crew repairs it.
  • Update and roll back go through the updater, the same path as Install now in the app. They also work when the app cannot be opened.
  • Uninstall has three levels. Stop removes nothing. Remove Crew keeps the data, the answers, the key and the secrets that open it, Docker, and Kata, so a new install opens the data again. Remove everything also deletes the data and the backups, and asks for the machine's name first.
  • Tested like a feature. Before a release, Crew is installed on a fresh virtual machine, runs a ticket with a fake agent, updates, rolls back, is uninstalled at each level, and is installed again. The test needs no DNS name and no login of yours.
Yours to decide

What is still open

What you answered in 0.32, the choices I made from it, and what stays open by design. Nothing here stops the build.

Choices I made from your answers

  • Crew chooses for five agents The builder, the reviewer, the tester, the E2E tester, and the verifier. The lead agents follow their list, because Crew has no measure yet for a plan.
  • One run in ten is a try That is how Crew gets numbers for the other models. It watches every change it makes, and goes back if it was worse.
  • An assistant answers in a ticket's chat Not the agent that works on the ticket, so a question never steers a run. Tell the agent is a button.
  • A sandbox is a Docker container with the Kata runtime As in styrman-crew today. Everything else of Crew is an ordinary container.
  • The chat comes with conversations In milestone 20, which can be built any time after milestone 8.

What you just decided

  • Docker only Everything runs in Docker, and Crew is built for nothing else.
  • A queue, by priority A lead run waits for a slot of its CLI, and the ticket with the higher priority goes first.
  • Automatic choice of model and CLI Crew chooses and tells you. Your own choice overrides it.
  • Improve text and Review text In planning, and on any text you select with the mouse.
  • A chat on every ticket Ask what happened, ask while it runs, and comment on text you mark.
  • Ready to build The kit and its start prompt were audited for that.

Decided before

  • Open-source Apache-2.0 source Compiled runtime images with vendor CLIs stay local or in your own private registry.
  • Two CLIs, and room for more agy and claude, each behind one adapter, with 2 lead slots each.
  • A release that changes code waits for you Only a release of prompts and harness text installs by itself.
  • Install, update, and uninstall are features One program, tested on a fresh machine.
  • Crew acts as you A sandbox works with your own logins.
  • Reviewed before the build. Two independent reviews read 0.29, and found 23 contradictions and 7 things that would have stopped the first install. A third read 0.30 for what still said that there is one CLI. What they found is corrected. A fourth read 0.31 against its seven changes, and found 19 contradictions and 13 gaps. Version 0.32 was audited before the build: one review read the design and the requirements, and another unpacked the build kit and followed its start prompt as a builder would. What they found is corrected. The spike and the first milestone are where it is tested.
  • The build started with a spike on the reference host, while styrman-crew is still there. Its sandboxes hold both CLIs. The spike settles what the design could not: what agy models prints, how claude gives its list of models, what claude prints at a limit, how long a rewrite of a prompt takes, whether its token works in ten sandboxes at once, whether a conversation continues in a new sandbox, and the host's real size.
  • Taking over a prior host. You copy out what you want to keep. Then styrman-crew's own uninstall removes it and keeps Docker, Kata, and its project data, and Crew is installed. From then until Crew can start a run, no agent runs on the host.
  • Named, and not designed yet. Budgets rest on token counts that agy reports best effort. A new approach by the lead skips the stages a ticket already passed. A day's backup holds the CLI's own files and the work folders.
  • Two CLIs, two accounts. When one CLI is signed out, at a limit, or its account is stopped, the agents move to the other. When both are down, every project waits. A limit of claude is known only when a run reaches it, until the spike finds a way to read what is left.
  • What the vendors say. For agy: headless use is intended for scripting and pipelines, and wrapping it in an application is not supported under consumer plans and can lead to suspension. For claude: signing in with a subscription is for ordinary, individual use of the unchanged program, and claude setup-token is documented for scripts. Many agents at once may be more than ordinary use. You decided to use both. On a machine that is not yours, whose accounts sign in is yours to decide for that machine.
  • The cost of your own logins in a sandbox. An agent that was tricked by something it read could read its CLI session files in the sandbox (gcloud was subsequently removed from all run sandboxes in design 0.79).
  • The cost of local backups. The database and its backups are on the same disk. If that disk dies, the tickets, the records, the conversations, and the trajectories are gone.
  • Still open with no rule: packages that agents install are only shown to the reviewer.

Your messages and the agent's answers, with what it did in its sandbox in each turn. Its trajectory is below the messages.

  • The sandbox: running, or removed and back with your next message
  • The CLI and the model, the id of the conversation at the CLI, and the command that continues it
  • Make a ticket of this, when it should reach the project
Crew › Inbox

Inbox

Everything that needs you, and everything that is about to go ahead by itself.

  • Each item says whether it needs you, goes ahead by itself, or is news
  • Each item has its alternatives as buttons, with Hold for a new feature and a release
  • Each item says how you were notified
Crew › Plans

Plans

Where a project starts. The plan is on one side, and the conversation with the planning agent on the other.

  • The first message shows that Crew's rewrite was sent, with your original one click away
  • The agent asks about what is still open
  • Create the project when the plan is right
Crew › Plans

Improve text, on a selection

You select text with the mouse and choose Improve text or Review text. On your own writing the prompt writer shows a better wording beside it, and nothing is sent until you send it. In planning, the first message gets a proposal by itself.

  • Use it, edit it, or keep your own
  • Review text changes nothing and says what is unclear or missing
  • On the plan itself, the request goes to the planning agent
Crew › Notifications

Notifications

Mail, to start with, and every message that was sent.

  • One mail for each thing that needs you, and one mail a day with the news
  • How a mail looks, and the two presses that answer it
  • Web push to a phone: later

Inside one project

Each project has its own board, agents, documentation, and knowledge. An agent in a project sees that project and nothing else.

project › Board

Board

One column per stage. Agents move the cards, not you. Amber means it needs you. Blue means an agent is working.

  • Each card: ticket number, kind, the agent on it with its model, and a live state
  • The stages of this project, with the optional ones marked
  • Add a ticket, change the stages, open the terminal
project › Tickets › SF-12

A ticket

The view that answers four questions: what is happening now, what was the agent told, where does this come from, and what has been done.

  • Running now: the agent, its model, its sandbox, its steps, and its log, live
  • Every subtask the ticket is using or has used, each with the prompt that agent was given
  • Why, what, goal, and checks. The part of the plan it comes from. The branch, the commits, and the diff.
  • Records: notes, reviews, test results, and your comments
project › Tickets › SF-15

A ticket with parallel subtasks

The lead split the build of this ticket. Three builders work at the same time, each in its own sandbox and on its own branch.

  • The subtasks say who created them, and on which branch each works
  • Crew joins the branches when the builders are done
project › Tickets

Tickets

The same tickets as a list, with the stage, the state, the agent, the cost, and how often each was sent back.

project › Tickets › a ticket

The chat of a ticket

Every ticket, running or done, has a chat. An assistant answers from the ticket's records, and text you mark comes in as a comment with a quote.

  • Ask what happened, or ask a question while it runs
  • Select text anywhere in the ticket and choose Comment
  • Tell the agent, Make a ticket of this, and Remember this
project › ticket › subtask

A run

One subtask in full: how the agent was started, which model it uses and where that was set, what its sandbox holds and may touch, the conversation it belongs to, the prompt, and its trajectory.

project › Board › Terminal

Terminal

A terminal in the browser, for looking into things. The repository is read-only until you switch on edit mode. From a ticket you jump straight into the sandbox where an agent is working.

project › Plan

Plan

The original plan and its parts, with the tickets that came from each. The plan is never edited after the OK.

project › Activity

Activity

A live feed for one project: runs starting and ending, moves, commits, reviews, created tickets, and decisions.

project › Agents

Agents

Every running sandbox in the project with its agent, model, ticket, and last step, and what waits for a slot, for room, or for a limit.

project › Documentation

Documentation

The pages every project keeps about itself. Agents write them with the change they describe, and they live in the repository.

project › Trajectories

Trajectories

The full record of every agent run in the project: every message, tool call, and result, kept in the database. Each row says which conversation the run continues, and opens the run.

project › Summaries

Summaries

What each finished ticket did and how it went. A separate step writes them, not the agent that did the work.

project › Tickets › a Done ticket

A finished ticket

The same view after the work. The outcome and the summary replace the running agent, and every subtask still has its prompt and its log.

project › Knowledge › Decisions

Decisions

Every choice an agent made by itself, with the alternatives and its reason. Agents do not wait for you. You can change any decision here, and Crew creates a ticket that carries the change out.

project › Knowledge

Knowledge

Memory, bugs, feedback, and evals. They belong to this project only. No other project can read them.

project › Analytics

Analytics

Flow, cost, and quality: tickets done, how many passed the first time, time in each stage, cost by agent.

project › Git

Git

The code: branches with how far each is ahead, the history with its trailers, tags, and pull requests. Tickets and records are not here. A local project can be connected to GitHub later.

project › Settings

Settings

The stages and their limits, the model and the effort for each role, the rule for checks, the project's own skills and context, the network mode, and who decides what.

project › Hosting

Hosting

Host locally, the address, who may open it, whether it may reach the internet, the running version and its health, the deploys with roll back, and the logs.

Crew itself

The level above the projects: learning, versions, logins, and the machine.

Crew › Crew level

Crew level

What Crew sees across all projects: how often you stepped in, how many checks passed the first time, and the signals by kind.

Crew › Crew level › Improvements

Improvements

What the improver proposed, the release it shipped in, and the measured effect. Each one opens to its evidence, its diff, and its evals.

Crew › Versions

Versions

The running version, the next release and whether it waits for you, every kept release with roll back, and the steps of the updater.

  • A release that changes code waits for Install
  • A release of prompts and harness text installs after 24 hours, unless you hold it
  • One number covers the server, the runtime image, both CLIs, the harness, and the stored format
Crew › Agent CLIs

Agent CLIs

One card for each CLI, agy and claude: signed in or not, the last check, and the version. Beside each, the limits of its groups of models. Below: what happens when a CLI cannot run, the rule for checks, and what a sandbox is given.

  • Each CLI has its own sign-in and limits
  • When one cannot run, the other takes the work it can
  • codex and opencode need an adapter, and are not built
Crew › Models

What Crew chose

At the top of Models: for each agent whether Crew chooses or you do, what Crew changed with its numbers, and what it would choose for an agent you set yourself.

  • Go back, or Set it myself
  • Use it, Back to Automatic, or Not now
  • One run in ten tries another model, and a comparison gets numbers faster
Crew › Models

Models

Every model the CLIs list themselves, by CLI and family. One model is open here: the agents that use it, what it has done, and its latest runs. Below it, the agents with the model, the effort, and the next choices of each.

  • Open any model
  • Give a model and an effort to an agent: the CLI comes with the model
  • Refresh reads the lists again
Crew › Setup

Setup

The first screen on a new machine, before any project, and where you sign in again: the machine check, and every credential: the git identity, the SSH key, gh, the GitHub App, gcloud, mail, agy, and claude.

Database

The brain of Crew: the container, every group of tables with its rows and how long they are kept, what is not in it, the backups, and the latest changes from the history.

Crew › Crew MCP

Crew MCP

Machine settings
