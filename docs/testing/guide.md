# Testing guide

Run from the repository root. No agent CLI is started and no microVM is needed, except where noted.

1. `make check` — Go tests of both modules (database tests on a throwaway PostgreSQL it starts), gofmt, vet, -race with a limit of 20 minutes per package, the UI's types and unit tests (`make test-web`), the firewall test, Compose config, version pins, plan copies, secret scan. `dbtest` copies a template database made once per test process. `internal/httpapi`'s tests run in parallel (`t.Parallel()`) where their state is their own, and a test that stays serial says why in a comment. Needs make, Python 3, Docker (via sudo), and a user namespace for the caller (Ubuntu: `kernel.apparmor_restrict_unprivileged_userns=0`).
1a. `make test-go-pkg PKG=…` — runs one Go package pattern under `-race -count=1` against `make check`'s throwaway PostgreSQL (`PKG` required, `GO_TEST_TIMEOUT` default `20m`, e.g. `make test-go-pkg PKG=./internal/httpapi/... GO_TEST_TIMEOUT=6m`).
2. UI build — in the pinned Node image (`WEB_NODE_IMAGE` in versions.lock): `npm ci && npm run build` in `web/`, run with `sudo docker run` as the caller's user. Its types and unit tests are in `make check`.
3. Installed-host check — `sudo deploy/crew-ctl status` and `sudo docker exec crew-server crew version` (must name the commit under test). Needs an installed Crew.
4. Browser tests — Playwright in the pinned image (`PLAYWRIGHT_IMAGE`), `tools/e2e/browser`, through the real ingress with the installation's JWT key from /etc/crew/secrets/jwt_key passed by environment (never printed). Fresh-installation-only tests ("first screen is Setup...", "Setup signs in the git identity") are excluded on an already initialized host. When running on the host itself, run the browser container on its own bridge (`docker run --add-host "<host>:host-gateway" --add-host "auth.<host>:host-gateway"`, not `--network host`): Chrome aborts a request in flight with `ERR_NETWORK_CHANGED` when the host gets a new bridge, which every microVM start creates. With `CREW_SHOTS` set to a mounted folder, the screens of M7 (`tests/screens.spec.ts`), M8 (`tests/models.spec.ts`: Models, the limits on Agent CLIs, the lead slots, a project's Settings, a ticket's agent), M12 (`tests/m12.spec.ts`: Knowledge with its tabs, Documentation, Settings' skills and context), and M15 (`tests/m15.spec.ts`: the Crew level with Signals, Improvements and an improvement, and Baseline; a project's Analytics; the Evals tab; the project's own baseline in Settings) save full-page screenshots to compare with `docs/plan/screens/`; their shared helpers are in `tests/helpers.ts`. These tests read and start nothing, except for `tests/m17.spec.ts` (M17: both settings screens, a change, its history, Put back), which modifies settings and so runs only with `CREW_E2E_WRITES=1` against a throwaway local stack (never against a live installation). In M17 it runs through `playwright.local.config.ts` against a throwaway stack alongside Crew (its own PostgreSQL, `crew serve` built from the checkout, and a Caddy proxy for `crew.test` injecting the ingress's headers; plan D28). The screens' own behaviour — no Put back on a read-only key and a fraction setting as a text field — is tested only there: make check runs the API's tests and `web/src/lib/settings.test.ts`'s helpers, not the components. The ingress answers 429 to a client past 100 requests a second, which a fast run reaches: the tests' API reads wait and ask again.
4a. Live checks — `npx playwright test -c playwright.live.config.ts` in `tools/e2e/browser`, the same way as the browser tests, with `CREW_PROJECT`, `CREW_TICKET`, or `CREW_DRAFT` passed by value (`-e NAME="$NAME"`: `sudo` drops the caller's environment). They run real calls on the operator's subscriptions or start microVMs, so they are never part of the browser tests and run only when the operator approved them: `live/prompt-writer.spec.ts` (two to three calls of the prompt writer and one run of the planning agent), `live/select.spec.ts` (two calls), `live/terminal.spec.ts` (a project terminal and one commit to `main`), `live/jump.spec.ts` (an agent must be running on the ticket), `live/gate.spec.ts` (the panel "The gate of V" on Versions while a gate's real ticket runs, with `CREW_GATE` the version; it reads and presses nothing, and costs nothing itself, but needs a gate whose live part runs). A marker a check waits for is one the shell computes, such as `$((40+2))`, so the echo of the typed line never matches.
5. Coverage — every changed file under cmd/, internal/, web/src/ needs a test beside it or covering it. The settings screens' components (`web/src/components/settingfield.tsx`, `signin.tsx`, `freshgate.tsx`, `web/src/routes/settings.tsx`, `p.$project.settings.tsx`) are covered by `tools/e2e/browser/tests/m17.spec.ts` alone, which make check does not run (item 4): a change to them owes that spec's run on the throwaway stack. The same holds for the screens of conversations (`web/src/components/chat.tsx`, `web/src/routes/conversations.tsx`, `conversations.$id.tsx`, and the task view's chat and marked text in `p.$project.tickets.$key.tsx`), covered by `tools/e2e/browser/tests/m20.spec.ts` alone (item 10).
6. Install test — `make install-test DISTRO=debian|ubuntu PHASE=…`: a fresh Debian or Ubuntu cloud image in QEMU with KVM, in a container on a sandbox bridge of its own (`sdb-installtest`, subnet 10.199.7.0/24), running `tools/install-test/inside.sh` as root; each step prints PASS or FAIL. Phases: `cycle` (install, update, rollback, uninstall), `kata4` (the move from Kata 3.31), `halfway`, `e2e`, `restart`, and `second` (16.12): `tools/install-test/second.sh` first builds two releases of the commit here with `crew-ctl build --out`, pushes Crew's images from this machine's Docker to a throwaway registry (`INSTALL_TEST_REGISTRY_IMAGE`) and serves them with TLS from a CA it makes and a made-up login, and writes their cards; the virtual machine installs from one card with the crew-ctl in its deploy archive, pulls the later card and installs it, and refuses a card whose image the registry swapped; it all is removed after. Each run needs the operator's yes: it takes up to an hour, and `second` builds on this machine.
7. Hosted bridges on real traffic — `sudo unshare -nm bash deploy/firewall/app-probe.sh` on a machine with Docker's modules: network namespaces of its own on an `app-` and an `apo-` bridge, the real `crew-firewall.sh`, and each connection tried; it prints PASS lines and PASS=n FAIL=0, and leaves nothing. A Kata guest on such a bridge needs machine setup 6 installed on the machine.
8. The Hosting tier — `make test-hosting` on a machine with Kata and the hosted bridges' chains (machine setup 6, or `crew-firewall.sh` of the checkout run once): `tools/hostingtier/stack.sh test` builds a throwaway stack of the checkout (`t19-server` with the Docker socket, `t19-db`, `t19-caddy` with internal certificates for `crew.test` and the made-up apps domain `apps.test`), seeds the project `t19app` with the busybox fixture, runs `go test -tags hosting ./tools/hostingtier` on the stack's network (E2E 1 to 6 and 8 of the M19 plan: real builds, real Kata microVMs, the ingress's routes, the four access choices, a failing deploy, a roll back with its data, a restart of Crew during a deploy, a restart of the hosted microVM, Stop), and removes all of it, the hosted sandboxes, their bridges and images included, whatever the test said. About six minutes. It pulls busybox from Docker Hub inside its build sandbox.
9. The Hosting screen — `tools/e2e/browser/tests/m19.spec.ts` on the m17 stack (see `tools/e2e/README.md`: start with `seed-hosting`, run `test m19.spec.ts`), which has no Docker: Roll back and the size in CPUs show only on the Hosting tier's stack.
10. Conversations and the chat of a ticket — `tools/e2e/browser/tests/m20.spec.ts` on the m17 stack (`seed-talk`, `test m20.spec.ts`): the Conversations screen and one conversation (convs.png, conv.png), Make a ticket of this adopting the agent's proposal, Remember this on the memory screen, Tell the agent from a conversation, a normal conversation about no project (with Live Crew map, Move to project backlog, Save, and Start a plan from this), Start and Delete, and the task view's chat on a running and a done ticket (chat.png in task.png and task-done.png) with marked text and Comment, Ask, the box's Tell the agent, and the ticket's history. The seed is rows only, so the build before reads the same state. The stack has no Docker: a message waits and no turn starts there, and the trajectory's events are not shown, since the runs' route answers 503 without Docker; the turns themselves are `make check`'s (`internal/assistant`, `internal/httpapi/m20_test.go`) and the real tier's.
11. The real tier of conversations — `make test-talk` on a machine with Kata, only with the operator's yes, since it runs real agy turns on the operator's subscription (plan M20 D24): at most six, five as written. The operator first puts agy's login file, as agy writes it at `~/.gemini/antigravity-cli/antigravity-oauth-token` and while its access token is fresh, at `.agents/scratch/t20/secrets/agy-login`, which git ignores; it is stored by path with `crew admin login set` in a container of its own, never printed, and removed with the stack (D39). `tools/talktier/stack.sh test` builds a throwaway stack of the checkout (`t20-server` with the Docker socket, `t20-db`), whose sandboxes start from the installed server's runtime image with this checkout's `crew-run` in it (`t20-runtime:dev`; the stack refuses to start when `image/` or `harness/` changed since that image's commit, which a dev build's tag names, and a release's tag `v<version>` or, with `updates.publish` off and so no tag, its release folder's `release.json`; `T20_BASE_COMMIT` names it by hand, BUG-017), seeds the paused project `t20app` with main and the ticket TA-1 at work on its branch, and runs `go test -tags talk ./tools/talktier` on the stack's network: a conversation about the project, whose sandbox is removed after `conversations.idle_minutes` (5 on the stack) and whose second message is answered in a new sandbox with the CLI's files and the work folder put back (E2E 1, 2); one about no project, with no single-project repository mounted in `/home/agent/work` and read-only Crew & map MCP (`get_crew_map`) (E2E 3); and two questions in TA-1's chat, the second in the same sandbox, reading the branch and calling `get_diff` (E2E 6's chat half). Crew runs no agy of its own there: `cli_logins` is seeded as checked a day ahead, so no scheduled login check is due; a guard removes every login-check sandbox of `t20-server` on its create event, and the tier fails on any line of `.agents/scratch/t20/logs/login-checks.log`; the project is paused, so no Analysis run, summary, improver or eval suite starts, and the test fails on a run of any role but the assistant. About fifteen minutes. All of it is removed whatever the test said.
Not run by make check: the install test, the hosted bridges' probe, the Hosting tier, and the real tier of conversations.
